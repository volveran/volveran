# A Broker Profile can connect with the Operator's own access token

[ADR 0004](0004-shared-broker-credentials-first.md) connected every Broker Profile with one shared service account, so the broker could not apply per-person permissions and its logs showed the account, not the person. v0.3 adds `credentials: operatorToken` as a per-profile option, in Team Mode only: Volverán keeps the access token the Operator got at sign-in in their server-side session, and every AMQP connection it opens for them on that profile (Checkout, Restore) uses it as the password, while every management API call sends it as a bearer token. RabbitMQ's OAuth 2.0 backend then checks the Operator's own scopes, and its connection list shows them. This supersedes ADR 0004 only for profiles that opt in: `shared` stays the default, and Solo Mode refuses `operatorToken` (it has no sign-in, so no token).

The option was gated on broker facts ([RabbitMQ behaviour](../rabbitmq-behaviour.md#oauth-20-tokens)), checked against a broker with the OAuth 2.0 backend only before any server work. The gate passed: a token works as the AMQP password (the broker user is taken from the token, whatever user name the client sends); `update-secret` accepts a refreshed token for the same user and refuses an invalid, expired or other user's token by closing the connection; a connection whose token expires without a refresh is closed at expiry with `320 CONNECTION_FORCED`; and the management API accepts the token as a bearer token.

## Decisions

- **One token per Operator, shared by every such profile.** Volverán has one OIDC client, so the one access token from sign-in serves every `operatorToken` profile. Each such broker must accept that token's audience and scopes (its `resource_server_id`, or `additional_scopes_key` / `scope_aliases`); per-profile clients, audiences and token exchange are out of scope.
- **The broker user in Audit Entries** is the token's `tokenUsernameClaim` (default `sub`, falling back to `sub` like RabbitMQ when the claim is missing). The profile's setting should match the broker's `auth_oauth2.preferred_username_claims`, so the Audit Entry names the user the broker's logs show.
- **A Checkout keeps its connection, and its owner.** The token is resolved when a connection opens and stays with that connection. An approved Apply runs on the requester's Checkout and connection ([Approval](../team-mode.md#approval)), so it acts with the requester's token and is recorded with the requester's broker user; the approver's broker permissions play no part.
- **Credentials are resolved per call, never cached** (`src/server/broker-credentials.ts`): the access check hands each route a management client and a credentials function, so a management call sends the current token, and an expired token is noticed when the broker is next used, not at sign-in.
- **The token refreshes itself and pushes the new one to live connections** (`src/server/operator-token.ts`). The session keeps the refresh token server-side with the access token, in one object held by the session's Operator and every Checkout they start. It refreshes 60 seconds before expiry (half the lifetime of a token shorter than two minutes), until the session ends, and tells every AMQP connection opened with it (a Checkout, a Restore in progress), which sends the new token with `update-secret` (`src/server/amqp-connection.ts`). The connection, its lock queue and its held Messages stay as they are: nothing reconnects. The `update-secret` answer is not awaited: the broker refuses a bad token by closing the connection, which the connection's close listener already reports, and amqplib never settles a refused `update-secret`.
- **With several Replicas, each refresh holds the session's row lock** (`SessionStore.refreshTokens`). Each Replica that has served the session keeps a live token and refreshes when it comes due. Under the lock, a Replica that finds a token in the store expiring later than its own takes it and pushes it to its connections with `update-secret`, without calling the provider, so a provider that rotates refresh tokens sees each one once. The lock is held across the call to the provider, so at most three refreshes per process run at once, leaving the store's connections for its other work; a sign-out waits for a refresh in progress. A request forwarded to another Replica names its session, never a token, and that Replica uses the session's token from the store.

## Failure modes

- **Refresh refused:** when the provider refuses the refresh grant (the refresh token was revoked or expired), or returns a token that would not expire later, Volverán stops refreshing and logs a warning naming the Operator (never a token). Other failures (the provider cannot be reached) are retried every 10 seconds while the token is valid. A provider that issues no refresh token gets no refresh: the access token runs out.
- **A Replica dies inside a refresh, on a provider that rotates refresh tokens:** the provider has rotated the token and the Replica dies before the store has it, since the lock is held across the call and the save comes after it. The store still holds the old refresh token, which the provider now refuses, so every other Replica's next refresh is refused as above. That Operator's token runs out and their live Checkouts are lost, on healthy Replicas too, until they sign in again. Reproduced by crashing a Replica 100 ms into a refresh; it stays a gap, and the [replica guide](../replicas.md) says so. A provider that accepts the old refresh token for a while avoids it.
- **Expired token, new work:** Volverán knows the token's expiry (`exp`), and any route that would reach the broker answers `401 broker_token_expired` with `signInUrl`; the web app asks the Operator to sign in again. Reading Volverán's own data (a Checkout already held, Audit Entries) still works.
- **Expired token, live Checkout:** the broker closes the connection at the token's expiry. That is a Lost Checkout through the existing path: the broker returns every Message to the queue (on quorum queues at the cost of one delivery), and the Checkout says why.
- **Missing broker permission:** a refused read of the queue when a Checkout starts, the configure permission for the lock queue, and the management tag answer `403 broker_permission_denied`, naming the profile, the broker user, the resource and the permission. A refused publish (write on the exchange) answers the same `403` on a Restore, whose Audit Entry is recorded as failed; during an Apply it fails that Message, as any other failed step does, with a reason naming the broker user, the exchange and the permission.
- **Token the broker does not accept** (audience, signing key): `authentication_failed`, as for wrong shared credentials, naming the Operator's token.

## Limits with several Replicas

- A refresh holds a lock and one store connection while it waits for the provider, at most 3 per process and 10 s each, so a slow provider delays other Operators' refreshes and nothing else. Past 10 s it counts as failed and is tried again; if the provider did act, a strict one may refuse the next try, and the Operator signs in again.
- A refreshed token that cannot be saved is logged and the process carries on with it. After a restart that Operator may have to sign in again.
- A token stored past its expiry answers the Operator's first request on a Replica `broker_token_expired`, as nothing has refreshed it yet.

## Consequences

- RabbitMQ's permissions, not only Volverán's roles, limit what each Operator can do on such a profile; the two are independent, and the narrower one wins.
- A Checkout outlives any number of token lifetimes, as long as the provider keeps refreshing; signing in again starts a new session and token, and does not rescue a Checkout whose token already ran out.
- The provider must issue a refresh token to Volverán's client (often only with the `offline_access` scope).
- Real deployments need an `https` JWKS endpoint (RabbitMQ refuses `http`) or a statically configured signing key; the Team Mode guide covers the set-up.
