# How a Checkout holds Messages on RabbitMQ 4.x

A Checkout holds Messages as unacknowledged deliveries instead of peeking with requeue, so looking at a Message costs it nothing. Verified against RabbitMQ 4.4.0 (see [`docs/rabbitmq-behaviour.md`](../rabbitmq-behaviour.md)), that choice needs the following mechanics:

- **Size.** A passive `queue.declare` gives the exact ready count N at once (management API figures lag by several seconds). Volverán caps N, sets prefetch to N, takes exactly N deliveries (the oldest) and cancels the consumer, so later arrivals stay in the queue.
- **One Checkout per queue.** Quorum queues ignore exclusive consumers, and single-active-consumer cannot be added to an existing queue. So the Checkout's connection declares an exclusive, auto-delete lock queue `volveran.checkout.<queue>`: another Volverán instance gets `RESOURCE_LOCKED`, and the broker releases the lock when the connection dies. The broker user therefore needs configure permission on `^volveran\.`.
- **Time limit.** Classic queues no longer time out consumers, so an abandoned Checkout would hold Messages forever. On quorum queues a timeout sends `basic.cancel` and later acks are silently ignored, so Apply would report work it never did. Volverán enforces its own time limit and ends the Checkout when the browser stops sending heartbeats. On quorum queues it sets `x-consumer-timeout` on its consumer just above that limit as a backstop. Because the Checkout cancels its own consumer once it holds N Messages, that backstop fires as a **channel close** (`406 PRECONDITION_FAILED`), not as `basic.cancel`; either signal, or a lost connection, makes the Checkout a Lost Checkout, which can no longer be Applied. The connection also needs an error handler: amqplib raises "Unknown consumer" if the broker cancels a consumer twice.
- **Returning Messages.** Keep and ending a Checkout use `nack` with requeue, one Message at a time in their original order. On quorum queues that costs no delivery attempt; a `reject` or a closed channel would. Only a crash or a lost connection uses up Delivery Budget.
- **Publishing.** Replay, Move and Restore publish on a separate confirm channel with `mandatory`. A publish error closes only that channel, never the one holding the Messages. A publish succeeds only when it is confirmed without a preceding `basic.return`, because unroutable Messages are returned and then still confirmed.
