# How a Checkout holds Messages on RabbitMQ 4.x

A Checkout holds Messages as unacknowledged deliveries instead of peeking with requeue, so looking at a Message costs it nothing. Verified against RabbitMQ 4.4.0 (see [`docs/rabbitmq-behaviour.md`](../rabbitmq-behaviour.md)), that choice needs the following mechanics:

- **Size.** A passive `queue.declare` gives the exact ready count N at once (management API figures lag by several seconds). Volverán caps N by the Message limit and takes at most N deliveries (the oldest), then cancels the consumer, so later arrivals stay in the queue. It asks for them in windows rather than with one prefetch of N, so large bodies cannot flood memory past the byte limit: each window is a new consumer on the same channel whose prefetch is the window (RabbitMQ does not widen a running consumer's prefetch; a new consumer continues in queue order), cancelled once it has delivered the whole window (a delivery after the cancel-ok would make amqplib fail the connection). The first window is 1; each next one is as many as the remaining bytes fit at the average body size so far, at most double what was delivered and never more than the rest of N. The byte limit applies to the exact body sizes: once a body does not fit, collection stops after that window, whose remaining deliveries overflow. Overflow (at most one window) is held hidden and returned right after the held Messages when the Checkout ends, which keeps the order on classic and quorum queues; the rest of N never left the queue.
- **One Checkout per queue.** Quorum queues ignore exclusive consumers, and single-active-consumer cannot be added to an existing queue. So the Checkout's connection declares an exclusive, auto-delete lock queue `volveran.checkout.<queue>`: another Volverán instance gets `RESOURCE_LOCKED`, and the broker releases the lock when the connection dies. The broker user therefore needs configure permission on `^volveran\.`.
- **Time limit.** Classic queues no longer time out consumers, so an abandoned Checkout would hold Messages forever. On quorum queues a timeout sends `basic.cancel` and later acks are silently ignored, so Apply would report work it never did. Volverán enforces its own time limit and ends the Checkout when the browser stops sending heartbeats. On quorum queues it sets `x-consumer-timeout` on each of its consumers just above that limit as a backstop. Because the Checkout cancels its own consumers once it has collected its Messages, that backstop fires as a **channel close** (`406 PRECONDITION_FAILED`), not as `basic.cancel`; either signal, or a lost connection, makes the Checkout a Lost Checkout, which can no longer be Applied. The connection also needs an error handler: amqplib raises "Unknown consumer" if the broker cancels a consumer twice.
- **Returning Messages.** Keep and ending a Checkout use `nack` with requeue, one Message at a time in their original order. On quorum queues that costs no delivery attempt; a `reject` or a closed channel would. Only a crash or a lost connection uses up Delivery Budget.
- **Publishing.** Replay, Move and Restore publish on a separate confirm channel with `mandatory`. A publish error closes only that channel, never the one holding the Messages. A publish succeeds only when it is confirmed without a preceding `basic.return`, because unroutable Messages are returned and then still confirmed.
