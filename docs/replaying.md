# Replaying many Messages

After an incident a dead-letter queue can hold hundreds of Messages, and the consumer they go back to has often only just recovered. Volverán has three ways to send them back without knocking it over again, each configured per Broker Profile (see `profiles.example.yaml`). Durations in the profiles file are a whole number and a unit: `30s`, `5m`, `1h30m`, `7d`.

**Throttled Replay.** A Broker Profile may set a **Replay Rate** (`replayRate: { default, max }`, in Messages per second): an Apply then starts its Replay and Move steps at least 1/rate apart, so the consumer gets a steady trickle instead of a burst. Discards are not slowed down. The Operator can pick another rate in the Apply confirmation, up to `max`, and sees how long the Apply will take; an Apply that would outlast the Checkout's time left is refused before it starts. While it runs, the Checkout shows the Messages done, failed and still to go, and the owner (or the approver of an approved Apply) can stop it: the step in progress finishes, and every Message not yet attempted goes back to the queue in its original order.

**Canary Replay.** An Apply can start with a **Canary**: one Replay carried out alone (the first Replay, or a Message the Operator picks), while every other Message stays held. Volverán then watches for the **Watch Window** (`canary: { watchWindow }`, from `5s` to `10m`, default `30s`) whether that Message is dead-lettered again, shows the outcome (died again with the new reason, not dead-lettered here within the Watch Window, or watch cut short when the Operator continues or stops before the window ends), and waits for the Operator to continue with the rest or stop, which returns the rest to the queue. The Checkout's time limit and heartbeat keep running while it waits. The watch reads nothing from the dead-letter queue: it binds a queue of its own to the dead-letter exchange, so it only sees a Message dead-lettered back through that exchange (direct, fanout or topic), or, for a MassTransit Message, through the `_error` exchange MassTransit publishes faults to ([Spring AMQP and MassTransit](spring-amqp-and-masstransit.md#replay-and-move)). With a headers exchange, no dead-letter exchange, or a refused permission, the Canary is unwatched, and the Apply confirmation says so beforehand. A Broker Profile can require a Canary for every Apply with more than a set number of Replays (`canary: { requiredAbove: N }`). On a Protected Profile in Team Mode, the Canary is part of the request for Approval: the approver sees it, approving runs it, and then either the requester or the approver continues or stops, with no second Approval.

**Replay rules.** A Broker Profile may declare **Replay rules** (`replayRules`, [ADR 0011](adr/0011-replay-rules-declared-in-the-profiles-file.md)): for one dead-letter queue, which Messages to Replay (any filter kind), how often to look, a back-off between attempts, an attempt limit counted from Died Again, what happens to the Messages that use it up (Keep, or Move to a parking queue), and a required automatic stop (`stopWhen`). Because rules live in the profiles file, a change to one goes through the same review as any other configuration change. Startup refuses an invalid rule with a message naming the profile, the rule and the key, and any rule on a profile with `credentials: operatorToken`. Each **Rule Pass** takes an ordinary Checkout as `Replay rule <name>` (skipped while someone holds the queue), Replays the matching Messages that are due at the rule's rate, Keeps the rest in order and ends; its Replays are Audit Entries naming the rule (search them with `rule=`). A rule pauses itself when too many of its Replays die again, when its queue is gone, or when the broker refuses its permissions or publishes. An `operator` can pause it with a reason (`POST /api/profiles/:profile/replay-rules/:name/pause`); only an `admin` resumes it (`…/resume`) or runs a pass now (`…/run`). Every pause and resume is an Audit Entry (`rule_pause`, `rule_resume`), and a pause survives restarts. The Replay rules view lists each profile's rules with their state, next pass and last passes. The [Replay rules guide](replay-rules.md) has worked examples.
