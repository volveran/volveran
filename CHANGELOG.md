# Changelog

All notable changes to Volverán are recorded here. The format is based on
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and Volverán follows
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- Set-up check `dead_letter_exchange_missing`: the queue list warns about a queue whose dead-letter exchange (by argument or policy) does not exist in the vhost, since the broker drops every Message the queue dead-letters. The queue list header counts the vhost's set-up warnings by severity. (#41)
- Roles per Broker Profile (Team Mode). A profile's optional `roles` maps OIDC groups to `viewer` (sees the profile, its queues and Audit Entries without Discarded bodies), `operator` (also reads Discarded bodies and starts Checkouts, Decisions and Apply) or `admin` (also Restores); the highest matching role wins. The groups come from the ID token claim named by `VOLVERAN_OIDC_GROUPS_CLAIM` (default `groups`; chart value `oidc.groupsClaim`) and are fixed until the next sign-in. Routes answer `403 no_role_on_profile` or `403 role_required` (with `required` and `held`) before touching the broker, `GET /api/profiles` and Audit Entry search leave out profiles without a role, `GET /api/session` gains `roles` and (Team Mode) `groups`, and every new Audit Entry records the Operator's `role` (`null` on older entries). The web app shows the actions a role does not allow as unavailable. Startup refuses unknown roles, empty group lists and non-string groups. **Upgrading changes nothing until you add `roles`:** a profile without them keeps every Operator `admin`, with a startup warning per profile ([ADR 0007](docs/adr/0007-profiles-without-roles-keep-everyone-admin.md)), and Solo Mode ignores them. (#38)
- The groups claim in the shapes identity providers send: `VOLVERAN_OIDC_GROUPS_CLAIM` takes a dotted path (`realm_access.roles` on Keycloak), a single string counts as one group, and when the ID token lacks the claim the groups are read from the provider's userinfo endpoint. A claim of any other shape, or a userinfo request that fails, gives no groups and a log warning, never a failed sign-in; startup refuses a path with an empty step. An Operator who signs in with no role on any Broker Profile sees a page saying so, listing the groups Volverán received. The Team Mode guide gains groups claim set-ups for Keycloak, JumpCloud, Okta and Entra ID (object ids, and the groups overage). (#39)
- Keyboard navigation. Queue list: `j`/`k` or the arrow keys move, Enter starts a Checkout on the focused queue. Checkout: `j`/`k` or the arrow keys move and the Message view follows, Space adds the focused Message to the Selection or takes it out, Shift+↑/↓ extends the Selection, Shift+`D`/`R`/`M`/`K` assign Discard, Replay, Move or Keep to the Selection or else the focused Message, `/` focuses the filter, Escape closes a prompt or clears the Selection, and `?` lists every shortcut. No key Applies, approves, rejects or Restores, and shortcuts do nothing while a text field has focus. The Message list is a listbox for screen readers, with the focused Message as its active descendant, and keyboard focus is always visible. (#47)

- Approval on Protected Profiles (Team Mode). An Apply with any Decision other than Keep on a Protected Profile waits for a second Operator with the role `operator` or `admin` on it. `POST /api/checkouts/:id/apply` answers `409 approval_required`; the requester confirms as before (typed queue name) with `POST /api/checkouts/:id/approval-request`, which freezes the Decisions (status `awaiting_approval`, `409 awaiting_approval` on a change) while the time limit and heartbeat keep running, and can withdraw it with `DELETE`. Approvers list the waiting Checkouts with `GET /api/approvals`, read one with `GET /api/approvals/:checkoutId` (and `/messages/:handle`), and approve it with `POST /api/approvals/:checkoutId/approve` `{ confirmQueueName }`, which runs the Apply on the requester's Checkout. Self-approval answers `403 cannot_approve_own_apply`. The Checkout view's `applyConfirmation` gains `approvalRequired`, `lastApply` gains `approvedBy`, and Audit Entries gain `approverId` and `approverName`. The web app's Apply confirmation becomes Request Approval, with a waiting state and Withdraw, and a new Approvals view reviews and approves. A profile gains `requireApproval` (only with `protected: true`; startup refuses it otherwise). (#45)

### Changed

- **Protected Profiles in Team Mode now require Approval by default.** After upgrading, an Apply that changes where a Message ends up on a Protected Profile waits for a second Operator, and startup logs which profiles require it. A team of one, or a profile where typed confirmation is enough, sets `requireApproval: false` on it to keep the v0.2 behaviour. Solo Mode is unchanged. (#45)
- Discard and Move open a prompt for the reason or the destination, the same prompt their keys open, instead of taking them from fields in the Decision bar. (#47)
- API: a queue list row's `setupWarning` (one warning or `null`) is now `setupWarnings`, a list (`[]` for none), so a queue shows every warning that applies. Each warning gains a `severity`: `loses_messages` or `may_lose_messages`. The delivery-limit warning keeps its code, `messages_dropped_at_delivery_limit`, and now also fires when the queue's dead-letter exchange does not exist. The queue list response gains `setupWarningCounts`, the warnings of the whole vhost by severity, whatever the search or dead-letter queue filter. (#41)

### Fixed

- Development: run from source (`npm run dev`), the server no longer serves the unbuilt `src/web` on `:8080`, which showed a blank page (`main.tsx` blocked for its MIME type). It serves no web app and answers `404` with a pointer to the Vite dev server on `http://localhost:5173`. `npm start` and the image still serve the built `dist/web`. (#32)

## [0.2.0] - 2026-10-27

Deployable on Kubernetes (see the [roadmap](ROADMAP.md)). The image and its behaviour are unchanged for `docker run` and Compose apart from the health endpoints and the numeric user.

### Added

- Helm chart `charts/volveran`, published to `oci://ghcr.io/volveran/charts/volveran` with the chart version equal to the Volverán version. It always runs Team Mode, listening on all interfaces inside the pod: one replica with the `Recreate` strategy (any other `replicaCount` is refused, citing ADR 0003), no service account token, a pod that passes the `restricted` Pod Security Standard (numeric non-root user, read-only root filesystem with an `emptyDir` at `/tmp`, no capabilities, `RuntimeDefault` seccomp), and liveness, readiness and startup probes on `/healthz` and `/readyz`. The OIDC client secret, the session secret and broker passwords come only from existing Secrets (`existingSecret`, `brokerProfiles.passwordsSecret`), never from values. Broker Profiles are written inline (a chart-managed ConfigMap whose changes roll the pod) or read from an existing ConfigMap. The audit store gets a PersistentVolumeClaim kept on uninstall, or an existing claim; `persistence.enabled: false` uses an `emptyDir` and warns in the install notes. Also: private CA bundles for brokers and the OIDC provider (`caBundles`), Volverán's settings as named values and an `extraEnv` escape hatch, image digest pinning and pull secrets, scheduling options, a values schema, install notes with the redirect URL to register, and every value documented in the chart README. Missing OIDC values or Broker Profiles fail at render time with a message naming the value. (#18, #22)
- Exposure: an optional Gateway API `HTTPRoute` (parent references, host names) and an optional `Ingress` (class, hosts, TLS Secrets, annotations); neither renders by default. (#20)
- An optional NetworkPolicy admitting only the peers you name to the pod, with optional egress rules that always allow DNS. (#21)
- Health endpoints: `GET /healthz` answers `200` whenever the process serves HTTP; `GET /readyz` answers `200` once configuration is loaded, OIDC discovery has succeeded (Team Mode) and the audit store is open (the server only starts listening after that), and `503` once shutdown starts. Both answer without a session in either mode, never check a broker, return only `{"status":"ok"}` and are left out of the request log. (#17)
- Signed artifacts: a version tag publishes the Helm chart next to the image, and the release workflow signs both with keyless cosign using its GitHub OIDC identity (verification commands and the Flux `matchOIDCIdentity` in the workflow's header). The release fails before anything is pushed unless the tag, `package.json` and the chart's `version` and `appVersion` agree. A pre-release tag (`v0.2.0-rc.1`) publishes a pre-release chart version. (#23)
- Kubernetes guide (`docs/kubernetes.md`): installing with Helm or Flux CD, values, exposure, secrets, private CAs, upgrades (a deploy signs everyone out and ends open Checkouts) and backup and restore of the audit store. A Flux CD example (`examples/flux/`): a namespace enforcing `restricted` pod security, a cosign-verified `OCIRepository` following `0.2.x`, a `HelmRelease` with OIDC, inline Broker Profiles, persistence and an `HTTPRoute`, and SOPS-encrypted Secrets with the reader's own age key. The Team Mode guide gains a Kubernetes section, and the README quick start the Helm install. (#24)
- A kind-cluster smoke test in CI (`npm run test:smoke`): the chart installs under restricted pod security, an Operator signs in and Applies a Checkout, the audit store survives a pod restart, and a changed Broker Profile rolls the pod. (#19)

### Changed

- The image runs as the numeric user `1000:1000` (the same `node` user as before), so Kubernetes can verify `runAsNonRoot`. Existing `/data` volumes stay writable. (#17)

## [0.1.0] - 2026-10-24

First release: triage core and identity (see the [roadmap](ROADMAP.md)).

### Added

- Solo Mode: no sign-in, listens on a loopback address only and refuses to start on any other. The Operator is taken from `VOLVERAN_OPERATOR`, else `USER`. (#2)
- Broker Profiles from a YAML file, with passwords from environment variables, `amqp`/`amqps` and `http`/`https`, and an optional CA file. (#2)
- Queue list per Broker Profile and vhost, with approximate depth, consumers and type; dead-letter queues first, streams marked as not available. (#2)
- Distinct connection errors for bad credentials, an unreachable broker, missing permissions and TLS failures. (#2)
- Docker image: multi-stage, runs as a non-root user and works with `--read-only`; Solo Mode runs with `--network host`. (#2)
- Release workflow: a tag `v<version>` publishes a multi-arch image (`linux/amd64`, `linux/arm64`) to `ghcr.io/volveran/volveran` as `<version>` and `latest`, with an SBOM and provenance attestations. (#13)
- README quick start and `docker-compose.example.yml`. (#13)
- Checkout: holds the N oldest ready Messages of a classic or quorum queue (N from a passive declare), unacknowledged, capped at 1,000 Messages or 100 MB of bodies (`VOLVERAN_CHECKOUT_MAX_MESSAGES`, `VOLVERAN_CHECKOUT_MAX_MB`); the UI shows "1,000 of ~N held". One Checkout per queue across instances, through an exclusive lock queue `volveran.checkout.<queue>` (needs configure permission on `^volveran\.`); a second one is refused and names the holder. One active Checkout per Operator. Ending it returns every Message to the queue in order, without using up Delivery Budget. Message list with `message_id`, routing key, timestamp, dead-letter reason, original queue and Delivery Budget on quorum queues; Message detail with properties, headers, `x-death` history and the body as JSON, text or hex and base64. (#3)
- Checkout time limit (`VOLVERAN_CHECKOUT_TIME_LIMIT_MINUTES`, default 30) shown as a countdown, and a browser heartbeat (`VOLVERAN_CHECKOUT_HEARTBEAT_SECONDS`, default 120): either ends the Checkout cleanly. On quorum queues the consumer carries `x-consumer-timeout` one minute past the time limit as a backstop. A Lost Checkout (connection dropped, channel closed, consumer cancelled by the broker) is reported with the Messages back in the queue, and Apply is refused. A queue with live consumers (counted with a passive declare) needs an explicit override to be checked out. (#4)
- Selection, filters and Decisions: filter the held Messages by routing key, header, `x-death` reason, original queue, body text and JSON path (a value at a path in a JSON body), select all matching, and give the Selection a Decision (Discard with a reason, Replay, Move or Keep). Decisions are held on the server for the Checkout, survive a browser reload, and are summarised for the Apply confirmation. Replay is unavailable, with the reason, for a Message with no `x-death` history. (#5)
- Protected Profiles (`protected: true` in a Broker Profile): highlighted throughout the UI; an Apply with any Decision other than Keep, and every Restore, needs the queue name typed, checked by the API as well as the UI. (#9)
- Team Mode (`VOLVERAN_AUTH=oidc`): sign-in through any OIDC provider (authorization code flow with PKCE, server-side sessions in an HTTP-only cookie, sign-out), every API route needs a session, and the Operator is the signed-in person (`sub` stored, email or name shown). Configured with `VOLVERAN_OIDC_*` and `VOLVERAN_SESSION_SECRET`; guide in `docs/team-mode.md`. (#11)
- Dead-letter set-up check: the queue list flags a quorum dead-letter queue with a delivery limit and no dead-letter exchange, where Messages past the limit are dropped, and suggests `delivery-limit = -1` or a dead-letter exchange. (#12)
- Apply with Discard: each Discarded Message is written in full (body, properties, headers) to the audit store with a durable commit, then acked; every other Message goes back to the queue in order. Each Message gets its own outcome (done, failed and kept, not attempted); there is no rollback, and Apply is refused on a Lost Checkout. (#6)
- Audit store: SQLite with schema migrations in `VOLVERAN_DATA_DIR` (`/data` volume in the image); an Audit Entry per action records the Operator, broker user, Broker Profile, vhost, queue, `message_id`, action, reason, outcome and time. Read through `GET /api/audit-entries` and `GET /api/audit-entries/:id`. (#6)
- Replay: a Message is published through the default exchange to the queue that dead-lettered it (its latest `x-death` entry), never to other queues bound to its routing key, on a separate confirm channel with `mandatory`, and acked only once confirmed without a return. `CC`, `BCC`, `x-death`, `x-first-death-*`, `x-last-death-*`, `x-delivery-count` and `x-acquired-count` are removed and `x-volveran-replay-id` and `x-volveran-from` added; the Audit Entry keeps the original headers. A Replay the broker cannot route fails and the Message falls back to Keep. (#7)
- Move: send Messages to another existing queue of the same vhost, or to an existing exchange with a routing key (delivered by its bindings), picked from the queues and exchanges of the vhost (`GET /api/profiles/:profile/vhosts/:vhost/move-destinations`). Same publish and header rules as Replay; the Audit Entry records the destination and the original headers. A destination that does not exist is refused when the Decision is given; an unroutable Move, or a destination deleted since, fails and the Message falls back to Keep. (#8)
- The Audit Entry of a Replay or Move records its replay id (`x-volveran-replay-id`), so a Message that dies again can be traced back: `GET /api/audit-entries?replayId=`. Audit store schema version 2. (#8)
- Audit browsing: search Audit Entries by Broker Profile, queue, `message_id`, action, Operator and date (`GET /api/audit-entries?profile=&queue=&messageId=&action=&operator=&from=&to=`), and by replay id (`replayId=`, #8), in a new Audit view of the web app that also shows each replay id. (#10)
- Restore: a Discarded Message is republished from its Audit Entry, byte for byte, to the queue it was Discarded from (default exchange) or to another existing queue, with the same header rules as Replay (`x-volveran-replay-id`, `x-volveran-from`), on a confirm channel with `mandatory`. Each Restore writes its own Audit Entry (action `restore`, linked to the Discard, with the replay id it published with) as the signed-in Operator; it is refused while the Discard is still being Applied, once it has been Restored, and, unless the Operator accepts a possible duplicate, when the Discard's outcome is pending or uncertain. A Protected Profile needs the destination queue name typed. `POST /api/audit-entries/:id/restore`. (#10)
- Retention of Discarded bodies: kept for 30 days or until they reach 1 GiB in total, whichever comes first, oldest evicted first, checked at startup and hourly (`VOLVERAN_BODY_RETENTION_DAYS`, `VOLVERAN_BODY_RETENTION_MAX_BYTES`, `VOLVERAN_BODY_RETENTION_INTERVAL_MINUTES`). Audit Entries are kept indefinitely; an evicted one shows "body expired" and Restore is refused with the reason (`410 body_expired`). `GET /api/audit-store` reports the stored size against the limit, and the Audit view warns at 90 %. Audit store schema version 3 adds `restore_of` and `body_expired_at`. (#10)
- Broker-facts suite: every fact in `docs/rabbitmq-behaviour.md` that the design depends on is checked against a real RabbitMQ, on every push against the pinned image and weekly against the latest `rabbitmq:4-management`. (#1)
