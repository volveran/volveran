# Changelog

All notable changes to Volverán are recorded here. The format is based on
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and Volverán follows
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

**Upgrading in Team Mode on PostgreSQL:** set the new `VOLVERAN_SESSION_ENCRYPTION_KEY` (chart: add `session-encryption-key` to the Secret named in `oidc.existingSecret`), or Volverán refuses to start. Nothing changes on SQLite or in Solo Mode.

### Changed

- With several Replicas, the metrics add up: the gauges of shared state (queue depth, set-up warnings, sampling, Alerts firing, Replay Rule state, stored body bytes) come from the Background Leader only, and counters stay per Replica. New metrics: `volveran_background_leader`, `volveran_forwarding_failures_total` and `volveran_audit_store_errors_total` ([guide](docs/observability.md#several-replicas)). A single Replica shows the same gauges as before, though on PostgreSQL they go away if it loses the store for longer than its lease. (#120)
- A pause now stops a Rule Pass in progress at its next step. The step under way finishes; the Messages not reached go back to the queue and count as Not due. It used to carry on and Replay them all. With several Replicas, Rule Passes run on the Background Leader, and a pause or resume works through any Replica. Audit schema v18 on SQLite. (#118)
- A stopping Replica gives notifications in progress up to 5 seconds to finish, then cuts them short and logs a warning. It used to cut them short at once, so a last automatic pause of a Replay Rule could go untold ([guide](docs/observability.md)). (#118)
- **Unknown keys in the profiles file are refused.** This is the deliberate breaking change of 1.0. A key the file does not have stops startup at every level, including the top level, a Broker Profile and a Replay rule's filter clause, where they used to be ignored, and the refusal names its path. A misspelt safety setting such as `requireAproval` can no longer silently leave it at its default. Try your file with `check-config` before upgrading ([guide](docs/configuration.md#unknown-keys)).
- `check-config` now exits `0` or `1`. It no longer exits `2`: an unknown key is something startup refuses, so it exits `1` and reports the first as an `error:` line, in place of a `refused in 1.0:` line for each.
- In Team Mode on PostgreSQL, sessions and sign-ins in progress live in the database, with their access and refresh tokens encrypted. An Operator stays signed in across a restart, and a sign-in or a sign-out works whichever Replica it reaches. On SQLite they stay in memory. (#107)

- The image is built on `node:24-alpine` instead of `node:24-slim` (Debian 12), which removes every high and critical finding of the image scan. An image you build on Volverán's now installs packages with `apk`, not `apt-get`, and has musl for its C library.

### Added

- The chart runs several Replicas: `replicaCount` above 1, with `postgres.existingSecret` and the new `forwarding.existingSecret`, gets a rolling update, a PodDisruptionBudget, topology spread (`pod.topologySpreadConstraints`), a headless Service and an internal port. Only other Replicas can reach that port: the chart always renders a NetworkPolicy saying so, whatever `networkPolicy.enabled` says, and it needs a CNI that enforces it. One replica renders as before, and `replicaCount` on SQLite stays at 1. [Running several Replicas](docs/replicas.md) says what failover protects and not, and what was tested: up to three Replicas. ADR 0014 supersedes ADR 0003. (#121)
- The API is served under `/api/v1`, and the web app uses it. `/api` stays as an alias through 1.x, so scripts from 0.x keep working, with the same sign-in, Role, Origin and forwarding checks. An answer's `auditUrl` and a refusal's text now name `/api/v1`. Each Release has an OpenAPI description, `openapi.json` ([guide](docs/configuration.md#the-http-api)). (#129)
- A Background Leader: one Replica holds a lease in the audit store and runs retention, the sampler and Alerts, and another takes over within 20 s if it goes away ([ADR 0014](docs/adr/0014-replicas-forwarding-and-the-background-leader.md)). It needs no Kubernetes API access. On SQLite it is simply its own leader, and nothing changes.
- The sampler runs on the Background Leader, so several Replicas take one set of Samples. Estimated arrivals count Messages taken out through every Replica, and a failover shows in the history view as a gap, with no false arrivals. On SQLite nothing changes.
- With `VOLVERAN_FORWARDING_SECRET`, `VOLVERAN_FORWARDING_PORT` and `VOLVERAN_FORWARDING_ADDRESS` set, in Team Mode on PostgreSQL, Replicas register in the database and an Operator's Checkout works through any of them, on an internal port that requires the shared secret: its view and heartbeat, reading Messages, Decisions, Apply, stop, Canary continue, a streamed export and ending it. Nothing changes without them, or on SQLite. (#108, #109)
- With Replicas, when an Owner Replica dies its Operators see a Lost Checkout with the reason through any other Replica, within the 15 s its lease holds, and an Apply it was running leaves `uncertain` Audit Entries for what is not known. While its lease is live but it cannot be reached, requests answer 503 `replica_unreachable`, to try again. A Replica that cannot renew its lease gives up its Checkouts. (#112)
- With Replicas, refreshing an Operator's access token on an `operatorToken` profile is safe with a provider that rotates refresh tokens: one Replica refreshes while holding the session's row, and the others use the new token, so a Checkout stays authenticated whichever Replica the Operator reaches, and Decisions work through any of them. (#114)
- AMQP connections ask for a 5 s heartbeat, unless a profile's `amqpUrl` names its own `heartbeat`. A lost host or network now holds a queue's lock and Messages for about 15 s rather than about three minutes. (#112)
- With those set, four-eyes works across Replicas: the Approvals view lists every waiting Approval from every Replica, and requesting, withdrawing, reading and comparing Messages, approving, rejecting, stopping, continuing and following an Apply work through any of them, with both people in the Audit Entries. (#111)
- With those set, the limit of one active Checkout per Operator holds across Replicas: a start on any of them is refused with `operator_has_checkout` while the Operator has a Checkout on another that is alive. (#110)
- With several Replicas, one notification goes out per Alert. A firing Alert survives a change of leader without being sent again as new. On PostgreSQL a notification in flight when the leader goes is sent again by the next, so it may arrive twice ([guide](docs/observability.md)). (#117)
- A JSON Schema of the profiles file, `profiles.schema.json`, attached to each GitHub Release ([guide](docs/configuration.md#the-schema-of-the-profiles-file)). A test holds it and the parser to the same fixtures; the parser stays the authority.

- A Replica shutting down reports not ready at once, refuses new Checkouts with `503` `replica_shutting_down`, and stops an Apply at its next step: the rest go back as Keep, reported `not-attempted`. Its Operators see through any Replica that the Checkout ended because the Replica shut down, where the other answered `checkout_not_found`. Before, an Apply in progress ran to its end. (#119)
- **The chart's `pod.terminationGracePeriodSeconds` default goes from 60 to 90**, to cover that at the default limits. A value you set stays, and should allow about 70 seconds at 1,000 Messages plus 40 ms for each one above. (#119)

### Fixed

- Stopping with a live Checkout no longer hangs when the broker connection has just dropped or the broker has gone silent: closing a channel or connection now has a time limit of 5 s. (#119)
- Ending a Checkout through Keep no longer uses up Delivery Budget on quorum queues, however it ends, including at shutdown. (#134) It now waits for the queue to take the Messages back before closing the channel, which took about 20 seconds per 1,000 Messages on a busy machine, so ending a large Checkout answers later. The wait stops after 40 ms per Message returned, at least 5 seconds (40 seconds at the default limit of 1,000 Messages), and logs a warning; another consumer on the queue can cause that, and any Message not yet taken back then costs one delivery. If you raise `VOLVERAN_CHECKOUT_MAX_MESSAGES`, raise `pod.terminationGracePeriodSeconds` to match.

### Security

- A state-changing request from a foreign `Origin` answers `403 foreign_origin`, on top of `SameSite=Lax`. In Team Mode the web app's origin is that of `VOLVERAN_OIDC_REDIRECT_URL` or `VOLVERAN_PUBLIC_URL`; API scripts send no `Origin` and are not affected. (#123)
- Solo Mode refuses a foreign `Host` (`403 foreign_host`, on the metrics port too) or `Origin` on every request, so a website cannot reach it through DNS rebinding. If you reach it through another name, set `VOLVERAN_PUBLIC_URL`. (#123)
- Sign-in no longer returns to another site through a tab or newline in `returnTo`. (#123)
- A [threat model](docs/threat-model.md), with the result of testing each finding of the security review and the risks accepted.
- Every answer now carries a strict `Content-Security-Policy` that also refuses framing, with `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` and `Referrer-Policy: no-referrer`, and `Strict-Transport-Security` when Volverán is reached over https (`VOLVERAN_PUBLIC_URL` or `X-Forwarded-Proto`). A hostile Message body or header cannot run script in an Operator's browser. Answers other than the web app's files are `Cache-Control: no-store`, so Message bodies stay out of the browser's cache. (#124)
- A [security policy](SECURITY.md) with a private way to report a vulnerability, a response time and supported versions.
- CI runs CodeQL, `npm audit` and an image scan on pull requests and every week, and scans the last released image every week. A release stops on a known high or critical finding in its dependencies or image, with a fix or without one, unless it is on the reviewed list in `.grype.yaml`.
- OIDC codes and `state` no longer reach the logs: a request's log line has its path without the query. (#125)
- An unhandled error answers a generic `internal_error` and logs the detail. A request Volverán cannot take keeps its status rather than answering 500: malformed or empty JSON `400 invalid_request`, a body over the limit `413 body_too_large`, an unsupported media type `415 unsupported_media_type`, a refusal from the static files `403 forbidden`. A sign-in that fails on Volverán's side says only that the provider's answer could not be used, with the reason in the log. (#125)
- In Team Mode, a session ends after `VOLVERAN_SESSION_IDLE_MINUTES` (default 60) without activity, on both audit stores, as well as 12 hours after sign-in. ([details](docs/configuration.md#session-idle-timeout), #125)
- The session guard reads the route, so `/%61pi/session` is refused like `/api/session`, and `/%61pi/checkouts/<id>` no longer answers 500 or tells an existing Checkout from an unknown one. (#126)
- `/auth/login` without a session can no longer add sign-ins in progress without limit: Volverán keeps the newest 10,000.
- The image no longer contains `npm` or `npx`, which nothing in it uses at runtime and which carried known high findings in their bundled packages.
- GitHub Actions are pinned by commit and the base image by digest, and Dependabot proposes their updates and those of npm dependencies.

## [0.6.1] - 2026-10-31

A queue can be Checked Out again straight after its Checkout ends.

**Upgrading from 0.6.0:** there is no store migration and no configuration change. The new image tag restarts the pod on upgrade, which ends open Checkouts. Ending a Checkout can take up to 3 seconds longer if another consumer attached during it.

**Known issue: ending a Checkout through Keep can use up Delivery Budget on quorum queues (#134).** It is not fixed in 0.6.1. Volverán closes the channel straight after returning the Messages, and closing it overtakes `nack`s still on their way: on the test broker most Messages past the first few dozen were counted as delivered ([RabbitMQ behaviour](docs/rabbitmq-behaviour.md#returning-messages-before-closing)). This applies however the Checkout ends with Messages still held, including at shutdown and so whenever the pod rolls, as it does on this upgrade. A Message on a queue with a finite `delivery-limit` can reach the limit sooner than its attempts suggest.

### Fixed

- A queue can be Checked Out again straight after its Checkout ends. The start could be refused with `checkout_in_progress`, naming no one, while the broker was still deleting the old lock queue.
- A queue with many Messages can also be Checked Out again straight after its Checkout ends. A quorum queue could still count the ended Checkout's consumers, so the start was refused with `queue_has_consumers`, and a Replay Rule's pass was recorded `failed`. Ending a Checkout now waits up to 3 seconds for them to clear.

## [0.6.0] - 2026-10-31

An asynchronous audit store, PostgreSQL as an alternative to SQLite, and `check-config`, all on one Replica (see the [roadmap](ROADMAP.md) and the [PostgreSQL guide](docs/postgresql.md)).

**Upgrading from 0.5:**

A profiles file and chart values from 0.5 keep working. PostgreSQL is optional and SQLite stays the default: without `VOLVERAN_POSTGRES_URL` (chart: `postgres.existingSecret`) the audit store stays where it is, and Solo Mode never needs a database server. These are all the things that change on their own:

- **An Apply stops after a failed store write.** Once the audit store fails a write, on either store, an Apply attempts no further step. The Message in progress finishes, and the rest are reported `not-attempted` and go back to their queue, where before each one was tried and failed in turn.
- **Some gauges can be up to 15 seconds old.** A metrics scrape no longer reads the audit store, so `volveran_replay_rule_paused`, `volveran_alerts_firing` and `volveran_audit_store_body_bytes` come from a reading taken in the background.
- **The chart's SQLite users see a version warning at startup.** On SQLite the chart renders the same profiles file as 0.5.1, so the file does not roll the pod, though a new image tag does, as on any upgrade. That file has no version. It is read as version 1 with a warning, harmless until 1.0. The chart writes `version: 1` only with `postgres.existingSecret`. With `brokerProfiles.existingConfigMap` the file is yours, and the same applies to it.
- **The SQLite store is migrated to schema version 17 at startup.** A store newer than the binary is now refused, so take a backup first if you may want to go back.

If you choose PostgreSQL:

- **`postgres.requireTls` defaults to `true`.** Volverán refuses a server that offers no TLS or a certificate that does not verify. Trust a private CA with `postgres.ca.bundle`, or set `postgres.requireTls: false` to leave TLS to the URL.

**Known issue: ending a Checkout through Keep can use up Delivery Budget on quorum queues.** It is not fixed in 0.6.0. Volverán closes the channel straight after returning the Messages, and closing it overtakes `nack`s still on their way: on the test broker most Messages past the first few dozen were counted as delivered ([RabbitMQ behaviour](docs/rabbitmq-behaviour.md#returning-messages-before-closing)). This applies however the Checkout ends with Messages still held, including at shutdown and so whenever the pod rolls. A Message on a queue with a finite `delivery-limit` can reach the limit sooner than its attempts suggest. Where the guides say Keep costs no Delivery Budget, this note takes precedence for 0.6.0.

### Added

- `check-config`, a mode of the image that checks a profiles file and the environment with the parser and checks startup uses, contacts no broker and exits 0, 1 (startup would refuse this) or 2 (1.0 will refuse a key in this file) ([guide](docs/configuration.md#checking-the-configuration)).
- The profiles file has a format version, `version: 1`. A file without it is still read as version 1, with a startup warning; any other version is refused. The chart writes it into the file it renders only on PostgreSQL.
- `VOLVERAN_POSTGRES_URL` keeps the audit store in PostgreSQL instead of SQLite: Audit Entries, Discarded bodies and their retention, Replay Rule state, depth history, notifications and Alerts. It answers as SQLite does, also for a NUL in a message id or other plain text. Without it nothing changes. See the new [PostgreSQL guide](docs/postgresql.md), which includes sizing.
- `copy-audit-store`, a mode of the image that copies a SQLite store of any released version into an empty PostgreSQL while Volverán is stopped, with ids and Discarded bodies, verifying each table's row count. The source is left byte for byte as it was: an older store is migrated in a temporary copy. A non-empty target is refused ([guide](docs/postgresql.md#copying-the-audit-trail)).
- Volverán sets `synchronous_commit` to `on` on its PostgreSQL connections, whatever the server's default, so a settled Audit Entry is durable.
- The chart keeps the audit store in PostgreSQL with `postgres.existingSecret`, reading the URL from that Secret, requiring TLS by default (`postgres.requireTls`), and trusting a mounted CA with `postgres.ca`. Then it renders no claim and no data volume. Without it the render does not change.
- `VOLVERAN_POSTGRES_REQUIRE_TLS` and `VOLVERAN_POSTGRES_CA_FILE` require TLS to PostgreSQL, with a verified certificate.
- On PostgreSQL, `/readyz` answers `503` while the database cannot be reached. Volverán reconnects by itself when it returns. `/healthz` does not change, and neither depends on a broker.

### Changed

- An Apply attempts no further step once the audit store fails a write, on either store. The Message in progress finishes, and the rest are reported `not-attempted` and go back to their queue, where before each one was tried and failed in turn.
- A Checkout's `endReason` has one more value, `start-failed`, for a Checkout whose search for Died Again Messages failed, which used to say `operator`. The API answers an error for such a start, so no view shows it today.
- Volverán refuses to start on an audit store newer than it understands, naming both versions. Downgrades were never supported, and now cannot damage the store.
- A metrics scrape no longer reads the audit store. `volveran_replay_rule_paused`, `volveran_alerts_firing` and `volveran_audit_store_body_bytes` come from a reading taken in the background, at most 15 seconds old ([metrics](docs/observability.md#metrics)).

### Deprecated

- 1.0 will refuse unknown keys at the top level of the profiles file and in a Broker Profile, which are ignored today. `check-config` lists them.

### Fixed

- A Checkout that could not start because the audit store failed while it looked for Died Again Messages no longer holds its queue, its Operator and its Messages until a restart.
- Rule badges no longer drop out of the Messages after a Decision is set, or in an approver's view of an Apply.

## [0.5.1] - 2026-10-30

A visual design for the web app. Behaviour, labels and keyboard shortcuts are unchanged. Releases now also publish their changelog entry as a GitHub Release.

### Changed

- The web app has a visual design. Labels are set in Atkinson Hyperlegible Next and data (queue names, `message_id`s, routing keys, headers, bodies) in Atkinson Hyperlegible Mono, both bundled, so nothing is fetched from another host. Every notice, panel and tag takes one level of a severity scale (info, warning, danger): Discard, typed confirmations, Reject, Stop, a Lost Checkout, Died Again, the last Delivery Budget attempt and set-up warnings that lose Messages are danger. A Protected Profile frames the whole window in red, over open prompts too. Each Message row carries a bar in its Decision's colour, and ComparisonView marks differences in a colour of their own. Light and dark themes meet WCAG AA contrast. No label, shortcut or focus behaviour changes.

## [0.5.0] - 2026-10-30

Observability (see the [roadmap](ROADMAP.md) and the [observability guide](docs/observability.md)): depth history of every dead-letter queue, Alerts to Slack, Microsoft Teams and webhooks, Prometheus metrics, and a Dead-letter Map.

**Upgrading from 0.4:**

A profiles file and chart values from 0.4 keep working unchanged. These are all the things that change on their own:

- **Sampling starts automatically.** Volverán reads the management API of every Broker Profile with shared credentials once a minute (`VOLVERAN_HISTORY_INTERVAL_SECONDS`), starting one interval after startup. It lists each profile's vhosts and queues, as the queue list does, and never takes a Checkout or reads a Message. Profiles with `credentials: operatorToken` are not sampled.
- **The audit store is migrated to schema version 16 at startup, and grows.** The migrations add tables for Samples, sampling runs, notifications and Alerts, and an index on Audit Entries (which takes a moment on a large store). A Sample takes about 100 bytes, so 100 dead-letter queues at the defaults add about 190 MiB over the first 14 days, then stay level ([sizing](docs/observability.md#sizing)). The chart's default `persistence.size` of 1 GiB equals the default limit on Discarded bodies, so check the claim before upgrading.
- **The retention job also removes** Samples, sampling runs and the outcomes of notifications older than `VOLVERAN_HISTORY_RETENTION_DAYS` (14 by default).
- **New in the web app and API, for everyone with a Role:** the depth chart in the queue list, and the history, Alerts and Dead-letter Map views and their endpoints. The queue list's response gains `depthSeries` and `firingAlerts` on dead-letter queues, and is otherwise unchanged.

**Nothing notifies anyone until you declare Alert Rules and Alert Destinations, and no metrics port opens until you set `VOLVERAN_METRICS_PORT` (chart: `metrics.enabled`).**

### Added

**Depth history**

- The sampler takes one Sample per dead-letter queue per run (the queue list's meaning: matching the profile's filter, dead-lettered into by other queues, or a MassTransit `_error` queue), and one sampling run per profile, independently, so a broker that cannot be reached delays no other. `VOLVERAN_HISTORY_INTERVAL_SECONDS` (default 60, 15 to 3600) and `VOLVERAN_HISTORY_RETENTION_DAYS` (default 14, 1 to 90) set it; the chart's `settings.historyIntervalSeconds` and `settings.historyRetentionDays` map to them. Audit schema v13. (#72, #73)
- Estimated arrivals: the change in depth since the Sample before, plus the Messages Volverán took out in between, never below zero. The broker does not count dead-lettered Messages in `message_stats.publish`, which the broker-facts suite proves and [RabbitMQ behaviour](docs/rabbitmq-behaviour.md#publish-counter) records. A consumer outside Volverán hides arrivals, and a queue's first Sample has unknown arrivals. (#71, #73)
- `GET /api/profiles/:profile/vhosts/:vhost/queues/:queue/history?from=&to=` (any Role on the profile) answers `{ from, to, retentionDays, latestSampleAt, samples, gaps, marks }`, downsampled to at most about 500 buckets of Samples. Default range 24 hours. An `operatorToken` profile answers `409 history_not_sampled`. (#73)
- A long range's bucket with some unknown arrivals, not all, says `arrivalsPartlyUnknown` and is hatched in the view. Each sampling run stores its interval (`interval_ms`), so changing the interval leaves old history's gaps as they were. A queue the management API lists with no depth, as it does for some seconds after a broker restart, gets no Sample in that run, holds its Alerts, and has unknown arrivals at its next Sample.
- The web app gains a 24-hour depth chart next to each dead-letter queue, with `depthSeries` in the queue list's response, and a history view (`#/history/...`, or `h` on the focused queue) over the last hour, 24 hours, 7 days or the whole retention, with depth, estimated arrivals, gaps and marks linking to the Audit view. Charts are inline SVG with a text summary. (#74)

**Alerts**

- `alertDestinations` at the top of the profiles file: `name`, `type` (`slack`, `teams` or `webhook`), `urlEnv`, and `signingSecretEnv` on a `webhook`. Startup refuses an unset variable. Deliveries have a 5-second timeout and up to 3 attempts, and their outcomes are kept in the audit store (schema v12). `VOLVERAN_PUBLIC_URL`, by default in Team Mode the origin of `VOLVERAN_OIDC_REDIRECT_URL`, starts the links in notifications. `POST /api/alert-destinations/:name/test` (`admin` on any profile) sends a test notification and answers with the outcome. The chart gains `brokerProfiles.alertDestinations` and `alerts.existingSecret`. See [ADR 0012](docs/adr/0012-alerting-declared-in-the-profiles-file.md). (#78)
- The generic webhook's documented JSON body, version 1, with `alertId`, `status`, `rule`, `profile`, `vhost`, `queue`, `condition`, `value`, `threshold`, `replayRule`, `reason`, `startedAt`, `endedAt`, `url` and `test` (`true` on a test notification, which your service should ignore), and with a signing secret `x-volveran-timestamp` and `x-volveran-signature`. See the [webhook schema](docs/observability.md#webhook-schema). (#78, #80)
- `alerts` on a Broker Profile: Alert Rules with `name`, `destinations`, `when`, `for` and `repeatEvery`. Queue conditions take `vhost` and `queue` or `queuePattern`, with `depthAbove`, `arrivalsAbove: { count, within }` or `anyArrival`. Alerts go from pending to firing to resolved, survive a restart without being sent again (schema v14), and are dropped quietly when their rule leaves the file. Arrival conditions count only arrivals the depth has borne out, so false spikes from lagging statistics do not fire them. (#79)
- Alert Rules on Volverán itself: `replayRulePaused: true` (optionally `rule`), `setupWarning: loses_messages | may_lose_messages` and `samplingFailing: { for }`. Startup refuses `replayRulePaused` on a profile with no Replay Rules, `setupWarning` and `samplingFailing` on an `operatorToken` profile, and a rule-level `for` on `samplingFailing`. Audit schema v15. (#80)
- The Alerts view shows firing and pending Alerts, the selected profile's Alert Rules and recent notifications with their outcomes, and lets an `admin` send a test notification. `GET /api/alerts` answers `{ alerts, notifications, destinations }` (`403 no_role` with no Role anywhere), and `GET /api/profiles/:profile/alert-rules` answers `{ rules }`. The queue list shows firing Alerts on their queue (`firingAlerts`). URLs and secrets never reach the browser. (#79, #80, #81)
- `GET /api/alerts`'s `notifications` carry `replayRule`, so Recent notifications names the Replay Rule of a paused-rule entry. A `queuePattern` that looks like a regular expression is refused at startup.

**Metrics**

- `VOLVERAN_METRICS_PORT` serves Prometheus metrics at `/metrics` on a port of its own, at `VOLVERAN_HOST`'s address, with no session. A scrape never contacts a broker. (#75)
- Families: `volveran_dead_letter_queue_messages`, `volveran_dead_letter_queue_estimated_arrived_messages_total`, `volveran_dead_letter_queue_setup_warnings`, `volveran_sampling_up`, `volveran_sampling_last_success_timestamp_seconds`, `volveran_replay_rule_paused`, `volveran_replay_rule_passes_total`, `volveran_apply_messages_total`, `volveran_checkouts_active`, `volveran_approvals_waiting`, `volveran_audit_store_body_bytes`, `volveran_alerts_firing`, `volveran_alert_notifications_total`, and the basics of `process_*` and `nodejs_*`. See the [metric reference](docs/observability.md#metric-reference). (#75, #77, #81)
- `volveran_dead_letter_queue_estimated_arrived_messages_total` counts arrivals once the depth has borne them out, as Alert Rules do, so management lag's false spikes never reach it and arrivals hidden by triage count one Sample late. The history keeps its estimate.
- The chart gains `metrics.enabled`, `metrics.port` (default 9464), `metrics.serviceMonitor` (`enabled`, `labels`, `interval`, `scrapeTimeout`) and `networkPolicy.metricsFrom`, which admits the scraper to the metrics port only. The `HTTPRoute` and `Ingress` never reference it. (#76)

**Dead-letter Map**

- `GET /api/profiles/:profile/vhosts/:vhost/dead-letter-map` (any Role on the profile) answers `{ nodes, edges, cycles }`: queues with depth, type, set-up warnings and whether a Checkout can be taken, exchanges, each edge with the `sources` that take it, drop edges for losses, `unresolved` edges where the set-up cannot tell, MassTransit `convention` edges, and the cycles Messages can really travel. (#72, #82)
- A Canary's watch queue is left out of the queue list, the map, sampling, metrics and Alerts, like a Checkout lock queue.
- The Dead-letter Map view (`#/dead-letter-map/<profile>/<vhost>`) draws it in columns as inline SVG, searches for a queue's connected part, links to history and Checkout, and lists the graph as text to copy. (#83)

### Changed

- A Replay Rule's pause reason reaches notifications and metrics; see the [Replay rules guide](docs/replay-rules.md#being-told-when-a-rule-pauses). Nothing about how rules run has changed.

## [0.4.0] - 2026-10-29

Replay at scale (see the [roadmap](ROADMAP.md)): Throttled Replay, Canary Replay, stopping an Apply part way, Replay rules, comparing two Messages, and the Failure Details of Spring AMQP and MassTransit.

**Upgrading from 0.3:**

- **API: Apply runs in the background and no longer returns its outcomes.** `POST /api/checkouts/:id/apply` and `POST /api/approvals/:checkoutId/approve` answer `202 { checkout }` with the Checkout's status `applying`, instead of `200 { checkout, outcomes }`. Scripts read the outcomes from `lastApply.outcomes` in the Checkout view (`GET /api/checkouts/:id`) once its status is no longer `applying`.

### Changed

- **API: Apply runs in the background and no longer returns its outcomes.** `POST /api/checkouts/:id/apply` and `POST /api/approvals/:checkoutId/approve` start the Apply and answer `202 { checkout }`, with the Checkout's status `applying`, instead of `200 { checkout, outcomes }`. Scripts read the outcomes from the Checkout view (`GET /api/checkouts/:id`) once its status is no longer `applying`: `lastApply.outcomes` has the same shape as before. Every refusal (`confirmation_required`, `queue_name_confirmation_required`, `approval_required`, `checkout_not_active`, `apply_in_progress`) still answers before anything starts. The Checkout view gains `applyProgress` (`total`, `done`, `failed`, `notAttempted`, `remaining`, `startedAt`, `estimatedEndAt`, `rate`, `stoppedBy` and `phase`). See [ADR 0009](docs/adr/0009-apply-runs-in-the-background-paced-between-steps.md). (#54)
- An Apply in progress no longer depends on the browser: the heartbeat window is suspended while it runs, so closing the page does not end the Checkout under it. The time limit stays a hard bound: at the limit the Apply attempts no further step, reports the rest `not-attempted` (back in the queue, in order) and the Checkout ends with `endReason: "time-limit"`; until now the time limit waited for the whole Apply. (#54)
- The web app starts the Apply (or approves it) and then follows its progress on the Checkout, with a progress bar of the Messages done, failed and still to go, and shows the outcome list once the Apply ends. An approver follows the progress and outcomes of the Apply they approved in the Approvals view. (#54, #55)
- Replay, Move and Restore also remove the Spring AMQP and MassTransit failure headers (`MT-Reason`, `MT-Fault-*`, `MT-Host-*`, `x-exception-*`, `x-original-exchange`, `x-original-routingKey`), as they already removed the dead-letter headers; the Audit Entry keeps the originals. (#61)

### Added

**Throttled Replay and stopping an Apply**

- A Replay Rate for an Apply, in Messages per second (`rate`, 0.1 to 1,000, in the bodies of `POST /api/checkouts/:id/apply` and `POST /api/checkouts/:id/approval-request`): its Replay and Move steps start at least 1/rate apart, between steps and never inside one, so ADR 0001's order is unchanged; Discards are not paced. A Broker Profile gains `replayRate: { default, max }`: `default` applies when the request gives none, and a rate above `max` (or no rate when `max` is set without `default` and the Apply has a Replay or Move step; a Discard-only Apply needs none) answers `400 rate_above_maximum` with `max`; startup refuses `default` above `max`. `applyConfirmation` gains `replayRate` and `estimatedDurationMs`, and an Apply that would outlast the Checkout's time left (less 10 s) answers `409 apply_would_outlast_checkout` with `neededMs` and `remainingMs`. The rate is frozen with the Decisions while awaiting Approval (`approvalRequest.rate`, and `rate` in `GET /api/approvals`), `applyProgress.rate` reports it, and every Audit Entry an Apply writes records it (`rate`, `null` when it ran with no Replay Rate; audit schema v7). The chart's values schema accepts `replayRate`. The web app gains a rate field in the Apply confirmation, prefilled from the profile, with the estimated duration, and shows the rate on the approval view, in the progress panel and in the Audit view. (#56)
- Stop an Apply in progress: `POST /api/checkouts/:id/apply/stop` (the owner), or `POST /api/approvals/:checkoutId/apply/stop` for the approver of an approved Apply. The step in progress finishes and no further step is attempted: the rest is reported `not-attempted` with the reason "Stopped by <name>…", falls back to Keep and goes back to the queue in its original order, and `applyProgress.stoppedBy` names who stopped it. With nothing left to stop (no Apply running, its last step reached, the Checkout lost, or the time limit or another Operator stopped it first) it answers `409 apply_not_running`; anyone else gets `403 not_checkout_owner` or the role errors. `GET /api/approvals/:checkoutId` keeps answering the approver for the Apply they approved, with its progress and then its outcomes. The web app's progress panel gains a Stop button with a confirmation, for the owner and, in the Approvals view, the approver. (#55)

**Canary Replay**

- The Apply body gains `canary: true | { handle }`: the Apply starts with one Replay carried out alone (the first Replay in Checkout order, or the picked Message, which must have the Decision Replay; `400 canary_needs_replay` when the plan has no Replay). Before publishing it, Volverán declares a watch queue `volveran.canary.<checkout id>` (exclusive, auto-delete) on the Checkout's connection and binds it to the source queue's dead-letter exchange with the bindings that route to the dead-letter queue (direct, fanout and topic only), recognising the copy by its `x-volveran-replay-id`; nothing is consumed from the dead-letter queue. `applyProgress.phase` moves to `canary_watch` for the Watch Window (cut short by a copy that died again), then `canary_done`, and the Checkout view's `canary` (`handle`, `messageId`, `auditEntryId`, `status`: `watching`, `died_again`, `not_dead_lettered`, `watch_cut_short` (Continue, Stop or the Checkout's end came before the Watch Window ended), `unwatched` or `failed`, `watchEndsAt`, `deadLetterReason`, `failureDetails`, `watchProblem`) shows the outcome. The Checkout stays active meanwhile, its Decisions frozen and its time limit and heartbeat running; `POST /api/checkouts/:id/apply/continue` carries out the rest at the Apply's rate (also before the window ends; `409 apply_not_waiting` otherwise), and the stop endpoint returns the rest to the queue as Keep, as does the Checkout ending or being lost while it waits. A headers dead-letter exchange, no dead-letter exchange or a refused permission makes the Canary `unwatched`, which `applyConfirmation.canary` (`watchWindowMs` and the candidates with their watchability) says beforehand. The Canary's Audit Entry records `canary: true` and `canaryOutcome` (audit schema v9). The broker behaviour the watch relies on, and how soon a Replayed Message can be dead-lettered again, are in [RabbitMQ behaviour](docs/rabbitmq-behaviour.md) and checked by the broker-facts suite. (#57, #58)
- A Broker Profile gains `canary: { watchWindow, requiredAbove }`. `watchWindow` is a duration from `5s` to `10m` (default `30s`). With `requiredAbove: N`, an Apply or request for Approval with more than N Replays and no Canary answers `400 canary_required` (`{ requiredAbove }`), and `applyConfirmation.canary` gains `requiredAbove` and `required`. Startup refuses other values; the chart's values schema accepts both. (#58, #59)
- Canary with Approval: the request for Approval accepts `canary` as an Apply does, frozen with the Decisions and the rate; `approvalRequest.canary` and the approval list's `canary` show it as `{ handle, messageId }`. Approving runs the Canary, and then the requester (`POST /api/checkouts/:id/apply/continue` or `…/stop`) or the approver (`POST /api/approvals/:checkoutId/apply/continue` or `…/stop`) continues or stops it, with no second Approval; every Audit Entry names both. (#59)
- The web app gains a Canary toggle and Message pick in the Apply confirmation (locked on when the profile requires a Canary), a Canary panel with a countdown, the outcome, and Continue and Stop, on the Checkout and on the approval view, the Canary in the approval list, and a Canary marker in the Audit view. (#58, #59)

**Comparing two Messages**

- `GET /api/checkouts/:id/compare?a=<handle>&b=<handle>` (the owner) and `GET /api/approvals/:checkoutId/compare?…` (an approver of the waiting Checkout) answer `{ left, right, diff }`: both Message views and their diff, with properties and headers by name (`equal`, `changed`, `onlyLeft`, `onlyRight`), `x-death` entries by position, Failure Details by field, and the body by kind (JSON as JSON-path changes, text as line hunks, binary as the sizes and first differing byte, bodies of different kinds as `mixed`). The role and owner rules are those of the Message view; an unknown handle answers `404 message_not_found`, the same handle twice `400 invalid_request`. The web app opens a two-column comparison from a Checkout with exactly two Messages selected (Compare, or the `c` key) and from the Approval view, with differences highlighted, "Hide equal" (on for bodies over 50 lines) and, in a Checkout, Decision buttons for each side. (#62)

**Spring AMQP and MassTransit**

- Failure Details. Volverán reads the headers Spring AMQP's `RepublishMessageRecoverer` (`x-exception-*`, `x-original-exchange`, `x-original-routingKey`) and MassTransit (`MT-Reason`, `MT-Fault-*`, `MT-Host-*`) write when they give up on a Message. Message summaries, the Message view and NDJSON export lines gain `failureDetails` (`null` when none; the export stays `v: 1`). Without `x-death`, the dead-letter reason falls back to the exception type and message, and the original queue to MassTransit's input queue. The new filter clause `{ "kind": "failure", "value": ... }` matches the exception type or message in any case. Queues whose name ends in `_error` are listed as dead-letter queues. The web app shows a Failure Details section (stack trace collapsed), a skipped marker for `MT-Reason: skip` and the Failure filter. See [Spring AMQP and MassTransit](docs/spring-amqp-and-masstransit.md). (#60)
- Replay origin from framework headers. Without `x-death`, a MassTransit Message is Replayed to its input queue (`MT-Fault-InputAddress`) through the default exchange, unless MassTransit skipped it (`MT-Reason: skip`: "no consumer handled this Message type") or the address names no queue; `x-death` still wins when present. A Spring AMQP Message is never Replayed: its `replay` gives a reason naming its original exchange and routing key and gains `suggestedMove` (`{ exchange, routingKey }`, or `{ queue }` for the default exchange), which prefills the web app's Move prompt. The Canary of a MassTransit Replay is watched on the `<input queue>_error` exchange, and is `unwatched` when that exchange is missing. See [ADR 0010](docs/adr/0010-replay-origin-from-framework-headers.md), which amends ADR 0005. (#61)

**Replay rules**

- A Broker Profile gains `replayRules` ([ADR 0011](docs/adr/0011-replay-rules-declared-in-the-profiles-file.md), [Replay rules guide](docs/replay-rules.md)): per rule a `name`, `vhost` and `queue`, an optional `filter` (one clause or a list, as in the API), `every` (30 s to 24 h), `maxPerPass` (default 100, at most the Checkout Message limit), `rate` (default 10, capped by `replayRate.max`), `backoff: { initial, multiplier, max }`, `maxAttempts` (1 to 100), `whenAttemptsUsedUp` (`keep` or `{ moveTo: { queue } }`), a required `stopWhen: { diedAgain, within }` and `startPaused`; durations are written `30s`, `5m`, `1h30m`. Startup refuses an invalid rule naming the profile, rule and key, and any rule on a profile with `credentials: operatorToken`; a rule on a Protected Profile is allowed and logged once. The chart's values schema accepts `replayRules` and refuses a rule without `stopWhen`. (#63)
- Rule Passes. The server runs each running rule every `every`, plus a small random jitter, counted from its last pass. A pass is an ordinary Checkout taken as the Operator `Replay rule <name>` (role `operator`): it Replays up to `maxPerPass` matching Messages whose back-off has passed (attempts counted from Died Again) at the rule's rate, without Approval or typed confirmation, Moves the Messages whose attempts are used up to `whenAttemptsUsedUp.moveTo` (with an ordinary Move Audit Entry) or Keeps them, Keeps the rest in order, and ends. A pass whose queue is held is skipped and recorded as skipped; shutdown waits for a pass in progress. While a pass holds a queue, the queue list and the "held by" answer name `Replay rule <name>`. Audit Entries gain `rule` and `rulePassId` (audit schema v8), and `GET /api/audit-entries` gains `rule`. (#63, #64)
- `GET /api/profiles/:profile/replay-rules` (`viewer`+) lists each rule with its declaration, `state` (`paused`, `pausedReason`, `pausedBy`, `pausedAt`), its last 20 `passes` (newest first, each with `status` `ran`, `skipped` or `failed`, a `reason`, and a `summary` of `held`, `replayed`, `usedUp`, `moved`, `notDue`, `noMatch`, `cannotReplay` and `failed`) and `nextPassAt`. `POST /api/profiles/:profile/replay-rules/:name/run` (`admin`) runs one pass now, also on a paused rule, and answers `{ pass }` once it has ended, or `409 checkout_in_progress` with the holder while the queue is held. Rule state lives in the audit store (audit schema v10): the paused flag (a rule with `startPaused` starts paused the first time, after which the stored state wins), the passes, and when a pass first saw each message id, the back-off's last fallback. A rule removed from the file is ignored and its state stays. (#63, #64)
- Automatic stop, pause and resume. After each pass, a rule pauses itself when `stopWhen.diedAgain` of its own Replays died again within `stopWhen.within` (`died_again`), when its queue is gone (`queue_not_found`), when the broker refuses its broker user a permission (`broker_permission_denied`, `lock_not_permitted`), or when a Replay or Move fails to publish (`publish_failed`). A due Message with no Replay origin (a Spring AMQP Message) is Kept and counted as `cannotReplay`, which never pauses the rule (audit schema v11). `POST /api/profiles/:profile/replay-rules/:name/pause` `{ reason }` (`operator`+) and `…/resume` (`admin`) pause and resume a rule (`409 replay_rule_paused` / `replay_rule_running`); resuming starts the automatic stop's count afresh. Every pause, automatic or not, and every resume is an Audit Entry with the new actions `rule_pause` and `rule_resume`, and a pause survives restarts. An Apply outcome the broker refused for lack of permission gains `refused: true`. (#65)
- Message rows and the Message view gain `rule: { name, attempts, maxAttempts, usedUp, nextAttemptAt }` when a running rule of the profile covers the queue and matches the Message. The web app gains a Replay rules view per profile, with each rule's state, why and by whom it paused, its next pass and pass history, and Run now, Pause and Resume as the role allows; a rule badge ("attempts used up" once the rule has given up) on Message rows and in the Message view; and a rule column and filter in the Audit view. (#63, #64, #65)

### Added

- Roles per Broker Profile (Team Mode). A profile's optional `roles` maps OIDC groups to `viewer` (sees the profile, its queues and Audit Entries without Discarded bodies), `operator` (also reads Discarded bodies and starts Checkouts, Decisions and Apply) or `admin` (also Restores); the highest matching role wins. The groups come from the ID token claim named by `VOLVERAN_OIDC_GROUPS_CLAIM` (default `groups`; chart value `oidc.groupsClaim`) and are fixed until the next sign-in. Routes answer `403 no_role_on_profile` or `403 role_required` (with `required` and `held`) before touching the broker, `GET /api/profiles` and Audit Entry search leave out profiles without a role, `GET /api/session` gains `roles` and (Team Mode) `groups`, and every new Audit Entry records the Operator's `role` (`null` on older entries; audit schema v4). The web app shows the actions a role does not allow as unavailable. Startup refuses unknown roles, empty group lists and non-string groups. **Upgrading changes nothing until you add `roles`:** a profile without them keeps every Operator `admin`, with a startup warning per profile ([ADR 0007](docs/adr/0007-profiles-without-roles-keep-everyone-admin.md)), and Solo Mode ignores them. Audit Entries of a profile no longer configured give the Operator the highest role they hold on any configured profile, so an Operator with no role anywhere neither finds them nor reads their bodies, and `GET /api/audit-store` answers `403 no_role` to such an Operator. (#38)
- The groups claim in the shapes identity providers send: `VOLVERAN_OIDC_GROUPS_CLAIM` takes a dotted path (`realm_access.roles` on Keycloak), a single string counts as one group, and when the ID token lacks the claim the groups are read from the provider's userinfo endpoint. A claim of any other shape, or a userinfo request that fails, gives no groups and a log warning, never a failed sign-in; startup refuses a path with an empty step. An Operator who signs in with no role on any Broker Profile sees a page saying so, listing the groups Volverán received. The Team Mode guide gains groups claim set-ups for Keycloak, JumpCloud, Okta and Entra ID (object ids, and the groups overage). (#39)
- Approval on Protected Profiles (Team Mode). An Apply with any Decision other than Keep on a Protected Profile waits for a second Operator with the role `operator` or `admin` on it. `POST /api/checkouts/:id/apply` answers `409 approval_required`; the requester confirms as before (typed queue name) with `POST /api/checkouts/:id/approval-request`, which freezes the Decisions (status `awaiting_approval`, `409 awaiting_approval` on a change) while the time limit and heartbeat keep running, and can withdraw it with `DELETE`. Approvers list the waiting Checkouts with `GET /api/approvals`, read one with `GET /api/approvals/:checkoutId` (and `/messages/:handle`), and approve it with `POST /api/approvals/:checkoutId/approve` `{ confirmQueueName }`, which runs the Apply on the requester's Checkout. Self-approval answers `403 cannot_approve_own_apply`. The Checkout view's `applyConfirmation` gains `approvalRequired`, `lastApply` gains `approvedBy`, and Audit Entries gain `approverId` and `approverName` (audit schema v5). The web app's Apply confirmation becomes Request Approval, with a waiting state and Withdraw, and a new Approvals view lists the waiting Checkouts, opens one read-only and approves it; it stays reachable (from the nav or a requester's link) while the approver has a Checkout of their own, which stays open meanwhile. A profile gains `requireApproval` (only with `protected: true`; startup refuses it otherwise). (#45)
- Reject a request for Approval with a reason: `POST /api/approvals/:checkoutId/reject` `{ reason }` (`400` without one) returns the Checkout to staging, and the Checkout view's `rejection` (`reason`, `rejectedBy`, `at`) shows it to the requester until the next request. `409 not_awaiting_approval` now says why the request no longer waits (withdrawn, approved, rejected, or cancelled by the Checkout ending, becoming lost or reaching its time limit), and approve, withdraw, reject and the Checkout's end are settled first-come. `GET /api/approvals` items gain `waitingMs`. The web app shows the rejection, the time left while waiting and a copyable link to the waiting Checkout (`/#/approvals/<checkout id>`), and the Approvals list shows waiting time, time left and the count of each Decision. (#46)
- Broker Profiles that connect with the Operator's own token (Team Mode). A profile with `credentials: operatorToken` has no `username` or `passwordEnv`: Volverán keeps the access token from sign-in in the server-side session, uses it as the password of every AMQP connection it opens for that Operator (Checkout, Restore) and as a bearer token for the management API, so RabbitMQ applies the person's own permissions and its logs show them. An approved Apply runs with the requester's token. The Audit Entry's broker user is the token claim named by `tokenUsernameClaim` (default `sub`). A broker permission refusal answers `403 broker_permission_denied` naming the resource and permission (a Restore the token may not publish included; in an Apply, a refused Replay or Move fails that Message with a reason naming the exchange and the write permission); an expired token answers `401 broker_token_expired` with `signInUrl`, and a live Checkout whose token expires becomes a Lost Checkout. Startup refuses `operatorToken` in Solo Mode and with `username` or `passwordEnv`; the chart's values schema accepts both keys. `GET /api/profiles` gains `credentials`, and `username` and `passwordEnv` are `null` on such a profile. See the Team Mode guide and [ADR 0008](docs/adr/0008-operator-token-pass-through-per-profile.md). (#49)
- Token refresh for `operatorToken` profiles. The session keeps the refresh token server-side and refreshes the access token 60 seconds before it expires (halfway through a token shorter than two minutes); every live AMQP connection the Operator opened on such a profile (a Checkout, a Restore in progress) receives the new token with `update-secret`, so a Checkout outlives the token on the same connection. When the provider refuses the refresh, the token runs out: routes answer `401 broker_token_expired`, the web app asks the Operator to sign in again, and a live Checkout ends as a Lost Checkout. Providers that issue a refresh token only for offline access need `offline_access` in `VOLVERAN_OIDC_SCOPES`. See [Token refresh](docs/team-mode.md#token-refresh). (#50)
- Died Again detection. A held Message carrying `x-volveran-replay-id` (one that Volverán Replayed, Moved or Restored and that was dead-lettered again) is flagged in the Checkout's Message list and the Message view with `diedAgain`: its replay id, how many times it has died again (followed back through the replay ids the earlier Audit Entries recorded), and the Audit Entry, action, time, Operator and source queue of the last trip out (`last`, `null` when no Audit Entry here has the replay id, e.g. another Volverán instance sent it, or when that entry is on a Broker Profile the Operator has no role on). The Checkout gains `diedAgainCount`, and the new filter clause `{ "kind": "died-again" }` selects these Messages for Select all matching. The web app shows a Died Again badge, links the Message view to the Audit Entry, offers the filter, and warns when Replay is given to a Died Again Message. No audit schema change. (#40)
- NDJSON export: the owner of an active Checkout downloads its held Messages, all of them or those matching the current filter, as one lossless JSON line each (`POST /api/checkouts/:id/export`, the Export buttons). Lines carry the properties and headers in the lossless AMQP JSON of Audit Entries, the body as base64, the decoded `x-death`, the Delivery Budget, the current Decision and the Died Again replay id. The download is streamed and changes nothing on the broker. Each export writes an Audit Entry with the new action `export`, the filter and the Message count (audit schema v6). The line format is in the README. (#44)
- Set-up check `dead_letter_exchange_missing`: the queue list warns about a queue whose dead-letter exchange (by argument or policy) does not exist in the vhost, since the broker drops every Message the queue dead-letters. The queue list header counts the vhost's set-up warnings by severity. (#41)
- Set-up check `dead_letter_unroutable`: the queue list warns about a queue whose dead-letter exchange exists but has no binding that routes its dead-letter routing key (or, without one, any routing key the queue is bound with) to a queue, and no alternate exchange, since the broker drops what the queue dead-letters. Direct, fanout and topic exchanges are evaluated, following exchange-to-exchange bindings; headers exchanges, exchanges of a plugin's type and the default exchange are never warned about. The warning carries `deadLetterExchange` and `routingKey` (`null` when the queue sets none). (#42)
- Set-up check `dead_letter_queue_drops_messages` (`loses_messages`): the queue list warns about a dead-letter queue with a message TTL or a length limit with `drop-head` overflow (the default) and no dead-letter exchange of its own, or with a queue expiry (`x-expires`), which deletes the queue and its Messages even when it has one. The warning's `settings` names which settings drop Messages. (#43)
- Set-up check `quorum_at_most_once_dead_lettering` (`may_lose_messages`): the queue list notes a quorum queue that dead-letters with the default `at-most-once` strategy (or `at-least-once` without the `reject-publish` overflow it needs), which can lose a dead-lettered Message, and explains the fix. Both checks read queue arguments and policies. (#43)
- Keyboard navigation. Queue list: `j`/`k` or the arrow keys move, Enter starts a Checkout on the focused queue. Checkout: `j`/`k` or the arrow keys move and the Message view follows, Space adds the focused Message to the Selection or takes it out, Shift+↑/↓ extends the Selection, Shift+`D`/`R`/`M`/`K` assign Discard, Replay, Move or Keep to the Selection or else the focused Message, `/` focuses the filter, Escape closes a prompt or clears the Selection, and `?` lists every shortcut. The Apply, Request Approval, Approve and Reject confirmations take the focus when they open (the typed queue name or reason, or else Cancel), close with Escape and give the focus back to the button that opened them. No key Applies, approves, rejects or Restores, and shortcuts do nothing while a text field has focus. The Message list is a listbox for screen readers, with the focused Message as its active descendant, and keyboard focus is always visible. (#47)

Broker Profiles are written inline (a chart-managed ConfigMap whose changes roll the pod) or read from an existing ConfigMap. The audit store gets a PersistentVolumeClaim kept on uninstall, or an existing claim; `persistence.enabled: false` uses an `emptyDir` and warns in the install notes. Also: private CA bundles for brokers and the OIDC provider (`caBundles`), Volverán's settings as named values and an `extraEnv` escape hatch, image digest pinning and pull secrets, scheduling options, a values schema, install notes with the redirect URL to register, and every value documented in the chart README. Missing OIDC values or Broker Profiles fail at render time with a message naming the value. (#18, #22)
- Exposure: an optional Gateway API `HTTPRoute` (parent references, host names) and an optional `Ingress` (class, hosts, TLS Secrets, annotations); neither renders by default. (#20)
- An optional NetworkPolicy admitting only the peers you name to the pod, with optional egress rules that always allow DNS. (#21)
- Health endpoints: `GET /healthz` answers `200` whenever the process serves HTTP; `GET /readyz` answers `200` once configuration is loaded, OIDC discovery has succeeded (Team Mode) and the audit store is open (the server only starts listening after that), and `503` once shutdown starts. Both answer without a session in either mode, never check a broker, return only `{"status":"ok"}` and are left out of the request log. (#17)
- Signed artifacts: a version tag publishes the Helm chart next to the image, and the release workflow signs both with keyless cosign using its GitHub OIDC identity (verification commands and the Flux `matchOIDCIdentity` in the workflow's header). The release fails before anything is pushed unless the tag, `package.json` and the chart's `version` and `appVersion` agree. A pre-release tag (`v0.2.0-rc.1`) publishes a pre-release chart version. (#23)
- Kubernetes guide (`docs/kubernetes.md`): installing with Helm or Flux CD, values, exposure, secrets, private CAs, upgrades (a deploy signs everyone out and ends open Checkouts) and backup and restore of the audit store. A Flux CD example (`examples/flux/`): a namespace enforcing `restricted` pod security, a cosign-verified `OCIRepository` following `0.2.x`, a `HelmRelease` with OIDC, inline Broker Profiles, persistence and an `HTTPRoute`, and SOPS-encrypted Secrets with the reader's own age key. The Team Mode guide gains a Kubernetes section, and the README quick start the Helm install. (#24)
- A kind-cluster smoke test in CI (`npm run test:smoke`): the chart installs under restricted pod security, an Operator signs in and Applies a Checkout, the audit store survives a pod restart, and a changed Broker Profile rolls the pod. (#19)

### Changed

- The image runs as the numeric user `1000:1000` (the same `node` user as before), so Kubernetes can verify `runAsNonRoot`. Existing `/data` volumes stay writable. (#17)

## [0.1.0] - 2026-10-24

First release: triage core and identity (see the [roadmap](ROADMAP.md)).

### Added

- Solo Mode: no sign-in, listens on a loopback address only and refuses to start on any other. The Operator is taken from `VOLVERAN_OPERATOR`, else `USER`. (#2)
- Broker Profiles from a YAML file, with passwords from environment variables, `amqp`/`amqps` and `http`/`https`, and an optional CA file. (#2)
- Queue list per Broker Profile and vhost, with approximate depth, consumers and type; dead-letter queues first, streams marked as not available. (#2)
- Distinct connection errors for bad credentials, an unreachable broker, missing permissions and TLS failures. (#2)
- Docker image: multi-stage, runs as a non-root user and works with `--read-only`; Solo Mode runs with `--network host`. (#2)
- Release workflow: a tag `v<version>` publishes a multi-arch image (`linux/amd64`, `linux/arm64`) to `ghcr.io/volveran/volveran` as `<version>` and `latest`, with an SBOM and provenance attestations. (#13)
- README quick start and `docker-compose.example.yml`. (#13)
- Checkout: holds the N oldest ready Messages of a classic or quorum queue (N from a passive declare), unacknowledged, capped at 1,000 Messages or 100 MB of bodies (`VOLVERAN_CHECKOUT_MAX_MESSAGES`, `VOLVERAN_CHECKOUT_MAX_MB`); the UI shows "1,000 of ~N held". One Checkout per queue across instances, through an exclusive lock queue `volveran.checkout.<queue>` (needs configure permission on `^volveran\.`); a second one is refused and names the holder. One active Checkout per Operator. Ending it returns every Message to the queue in order, without using up Delivery Budget. Message list with `message_id`, routing key, timestamp, dead-letter reason, original queue and Delivery Budget on quorum queues; Message detail with properties, headers, `x-death` history and the body as JSON, text or hex and base64. (#3)
- Checkout time limit (`VOLVERAN_CHECKOUT_TIME_LIMIT_MINUTES`, default 30) shown as a countdown, and a browser heartbeat (`VOLVERAN_CHECKOUT_HEARTBEAT_SECONDS`, default 120): either ends the Checkout cleanly. On quorum queues the consumer carries `x-consumer-timeout` one minute past the time limit as a backstop. A Lost Checkout (connection dropped, channel closed, consumer cancelled by the broker) is reported with the Messages back in the queue, and Apply is refused. A queue with live consumers (counted with a passive declare) needs an explicit override to be checked out. (#4)
- Selection, filters and Decisions: filter the held Messages by routing key, header, `x-death` reason, original queue, body text and JSON path (a value at a path in a JSON body), select all matching, and give the Selection a Decision (Discard with a reason, Replay, Move or Keep). Decisions are held on the server for the Checkout, survive a browser reload, and are summarised for the Apply confirmation. Replay is unavailable, with the reason, for a Message with no `x-death` history. (#5)
- Protected Profiles (`protected: true` in a Broker Profile): highlighted throughout the UI; an Apply with any Decision other than Keep, and every Restore, needs the queue name typed, checked by the API as well as the UI. (#9)
- Team Mode (`VOLVERAN_AUTH=oidc`): sign-in through any OIDC provider (authorization code flow with PKCE, server-side sessions in an HTTP-only cookie, sign-out), every API route needs a session, and the Operator is the signed-in person (`sub` stored, email or name shown). Configured with `VOLVERAN_OIDC_*` and `VOLVERAN_SESSION_SECRET`; guide in `docs/team-mode.md`. (#11)
- Dead-letter set-up check: the queue list flags a quorum dead-letter queue with a delivery limit and no dead-letter exchange, where Messages past the limit are dropped, and suggests `delivery-limit = -1` or a dead-letter exchange. (#12)
- Apply with Discard: each Discarded Message is written in full (body, properties, headers) to the audit store with a durable commit, then acked; every other Message goes back to the queue in order. Each Message gets its own outcome (done, failed and kept, not attempted); there is no rollback, and Apply is refused on a Lost Checkout. (#6)
- Audit store: SQLite with schema migrations in `VOLVERAN_DATA_DIR` (`/data` volume in the image); an Audit Entry per action records the Operator, broker user, Broker Profile, vhost, queue, `message_id`, action, reason, outcome and time. Read through `GET /api/audit-entries` and `GET /api/audit-entries/:id`. (#6)
- Replay: a Message is published through the default exchange to the queue that dead-lettered it (its latest `x-death` entry), never to other queues bound to its routing key, on a separate confirm channel with `mandatory`, and acked only once confirmed without a return. `CC`, `BCC`, `x-death`, `x-first-death-*`, `x-last-death-*`, `x-delivery-count` and `x-acquired-count` are removed and `x-volveran-replay-id` and `x-volveran-from` added; the Audit Entry keeps the original headers. A Replay the broker cannot route fails and the Message falls back to Keep. (#7)
- Move: send Messages to another existing queue of the same vhost, or to an existing exchange with a routing key (delivered by its bindings), picked from the queues and exchanges of the vhost (`GET /api/profiles/:profile/vhosts/:vhost/move-destinations`). Same publish and header rules as Replay; the Audit Entry records the destination and the original headers. A destination that does not exist is refused when the Decision is given; an unroutable Move, or a destination deleted since, fails and the Message falls back to Keep. (#8)
- The Audit Entry of a Replay or Move records its replay id (`x-volveran-replay-id`), so a Message that dies again can be traced back: `GET /api/audit-entries?replayId=`. Audit store schema version 2. (#8)
- Audit browsing: search Audit Entries by Broker Profile, queue, `message_id`, action, Operator and date (`GET /api/audit-entries?profile=&queue=&messageId=&action=&operator=&from=&to=`), and by replay id (`replayId=`, #8), in a new Audit view of the web app that also shows each replay id. (#10)
- Restore: a Discarded Message is republished from its Audit Entry, byte for byte, to the queue it was Discarded from (default exchange) or to another existing queue, with the same header rules as Replay (`x-volveran-replay-id`, `x-volveran-from`), on a confirm channel with `mandatory`. Each Restore writes its own Audit Entry (action `restore`, linked to the Discard, with the replay id it published with) as the signed-in Operator; it is refused while the Discard is still being Applied, once it has been Restored, and, unless the Operator accepts a possible duplicate, when the Discard's outcome is pending or uncertain. A Protected Profile needs the destination queue name typed. `POST /api/audit-entries/:id/restore`. (#10)
- Retention of Discarded bodies: kept for 30 days or until they reach 1 GiB in total, whichever comes first, oldest evicted first, checked at startup and hourly (`VOLVERAN_BODY_RETENTION_DAYS`, `VOLVERAN_BODY_RETENTION_MAX_BYTES`, `VOLVERAN_BODY_RETENTION_INTERVAL_MINUTES`). Audit Entries are kept indefinitely; an evicted one shows "body expired" and Restore is refused with the reason (`410 body_expired`). `GET /api/audit-store` reports the stored size against the limit, and the Audit view warns at 90 %. Audit store schema version 3 adds `restore_of` and `body_expired_at`. (#10)
- Broker-facts suite: every fact in `docs/rabbitmq-behaviour.md` that the design depends on is checked against a real RabbitMQ, on every push against the pinned image and weekly against the latest `rabbitmq:4-management`. (#1)
