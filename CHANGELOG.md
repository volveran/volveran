# Changelog

All notable changes to Volverán are recorded here. The format is based on
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and Volverán follows
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed

- **API: Apply runs in the background and no longer returns its outcomes.** `POST /api/checkouts/:id/apply` and `POST /api/approvals/:checkoutId/approve` start the Apply and answer `202 { checkout }`, with the Checkout's status `applying`, instead of `200 { checkout, outcomes }`. Scripts read the outcomes from the Checkout view (`GET /api/checkouts/:id`) once its status is no longer `applying`: `lastApply.outcomes` has the same shape as before. Every refusal (`confirmation_required`, `queue_name_confirmation_required`, `approval_required`, `checkout_not_active`, `apply_in_progress`) still answers before anything starts. The Checkout view gains `applyProgress` (`total`, `done`, `failed`, `notAttempted`, `remaining`, `startedAt`, `estimatedEndAt`, and `rate` and `stoppedBy`, both `null` for now). See [ADR 0009](docs/adr/0009-apply-runs-in-the-background-paced-between-steps.md). (#54)
- An Apply in progress no longer depends on the browser: the heartbeat window is suspended while it runs, so closing the page does not end the Checkout under it. The time limit stays a hard bound: at the limit the Apply attempts no further step, reports the rest `not-attempted` (back in the queue, in order) and the Checkout ends with `endReason: "time-limit"`; until now the time limit waited for the whole Apply. (#54)
- The web app starts the Apply (or approves it) and then follows its progress on the Checkout, with a progress bar of the Messages done, failed and still to go, and shows the outcome list once the Apply ends. An approver sees that the Apply started on the requester's Checkout, where its progress and outcomes are shown. (#54)

### Added

- Replay rules, declared and run on demand. A Broker Profile gains `replayRules`: per rule a `name`, `vhost` and `queue`, an optional `filter` (one clause or a list, as in the API), `every` (30 s to 24 h), `maxPerPass` (default 100, at most the Checkout Message limit), `rate` (default 10, capped by `replayRate.max`), `backoff: { initial, multiplier, max }`, `maxAttempts` (1 to 100), `whenAttemptsUsedUp` (`keep` or `{ moveTo: { queue } }`), a required `stopWhen: { diedAgain, within }` and `startPaused`; durations are written `30s`, `5m`, `1h30m`. Startup refuses an invalid rule naming the profile, rule and key, and any rule on a profile with `credentials: operatorToken`; a rule on a Protected Profile is allowed and logged once. `POST /api/profiles/:profile/replay-rules/:name/run` (`admin`) runs one Rule Pass: an ordinary Checkout taken as the Operator `Replay rule <name>` (role `operator`), which Replays up to `maxPerPass` matching Messages whose back-off has passed (attempts counted from Died Again) at the rule's rate, without Approval or typed confirmation, Keeps the rest in order, and answers `{ pass: { id, at, summary: { held, replayed, usedUp, notDue, noMatch, failed } } }`, or `409 checkout_in_progress` with the holder while the queue is held. `GET /api/profiles/:profile/replay-rules` (`viewer`+) lists the rules with their last pass. While a pass holds a queue, the queue list and the "held by" answer name `Replay rule <name>`. Audit Entries gain `rule` and `rulePassId` (audit schema v8), and `GET /api/audit-entries` gains `rule`. The chart's values schema accepts `replayRules` and refuses a rule without `stopWhen`. The web app gains a Replay rules view per profile with Run now, and a rule column and filter in the Audit view. ADR 0011 records the choices. (#63)
- Replay rules run on their own schedule and keep their state. The server runs each running rule every `every`, plus a small random jitter, counted from its last pass; a pass whose queue is held is skipped and recorded as skipped, and shutdown waits for a pass in progress. A Message whose attempts are used up is Kept, or with `whenAttemptsUsedUp: { moveTo: { queue } }` Moved there with an ordinary Move Audit Entry naming the rule. Rule state lives in the audit store (audit schema v10): the paused flag (a rule with `startPaused` starts paused the first time, after which the stored state wins), the last 20 passes, and when a pass first saw each message id, the back-off's last fallback. A rule removed from the file is ignored and its state stays. `GET /api/profiles/:profile/replay-rules` now lists each rule with `state`, `passes` (newest first, each with `status` `ran`, `skipped` or `failed`, a `reason`, and a `summary` that gains `moved`) and `nextPassAt`, in place of `lastPass`. Message rows and the Message view gain `rule: { name, attempts, maxAttempts, usedUp, nextAttemptAt }` when a running rule of the profile covers the queue and matches the Message. The web app shows each rule's state, next pass and pass history, and a rule badge ("attempts used up" once the rule has given up) on Message rows and in the Message view. (#64)
- Throttled Replay. An Apply can be given a Replay Rate in Messages per second (`rate`, 0.1 to 1,000, in the bodies of `POST /api/checkouts/:id/apply` and `POST /api/checkouts/:id/approval-request`): its Replay and Move steps then start at least 1/rate apart, between steps and never inside one, so ADR 0001's order is unchanged; Discards are not paced. A Broker Profile gains `replayRate: { default, max }`: `default` applies when the request gives none, and a rate above `max` (or no rate when `max` is set without `default`) answers `400 rate_above_maximum` with `max`; startup refuses `default` above `max`. `applyConfirmation` gains `replayRate` and `estimatedDurationMs`, and an Apply that would outlast the Checkout's time left (less 10 s) answers `409 apply_would_outlast_checkout` with `neededMs` and `remainingMs`. The rate is frozen with the Decisions while awaiting Approval (`approvalRequest.rate`, and `rate` in `GET /api/approvals`), `applyProgress.rate` reports it, and every Audit Entry an Apply writes records it (`rate`, `null` when unthrottled; audit schema v7). The chart's values schema accepts `replayRate`. The web app gains a rate field in the Apply confirmation, prefilled from the profile, with the estimated duration, and shows the rate on the approval view, in the progress panel and in the Audit view. (#56)
- Stop an Apply in progress: `POST /api/checkouts/:id/apply/stop` (the owner), or `POST /api/approvals/:checkoutId/apply/stop` for the approver of an approved Apply. The step in progress finishes and no further step is attempted: the rest is reported `not-attempted` with the reason "Stopped by <name>…", falls back to Keep and goes back to the queue in its original order, and `applyProgress.stoppedBy` names who stopped it. With nothing left to stop (no Apply running, its last step reached, the Checkout lost, or the time limit or another Operator stopped it first) it answers `409 apply_not_running`; anyone else gets `403 not_checkout_owner` or the role errors. `GET /api/approvals/:checkoutId` keeps answering the approver for the Apply they approved, with its progress and then its outcomes. The web app's progress panel gains a Stop button with a confirmation, for the owner and, in the Approvals view, the approver. (#55)
- Canary Replay. The Apply body gains `canary: true | { handle }`: the Apply starts with one Replay carried out alone (the first Replay in Checkout order, or the picked Message, which must have the Decision Replay; `400 canary_needs_replay` when the plan has no Replay). Before publishing it, Volverán declares a watch queue `volveran.canary.<checkout id>` (exclusive, auto-delete) on the Checkout's connection and binds it to the source queue's dead-letter exchange with the bindings that route to the dead-letter queue (direct, fanout and topic only), recognising the copy by its `x-volveran-replay-id`; nothing is consumed from the dead-letter queue. `applyProgress.phase` moves to `canary_watch` for the Watch Window (cut short by a copy that died again), then `canary_done`, and the Checkout view's `canary` (`handle`, `messageId`, `auditEntryId`, `status`: `watching`, `died_again`, `not_dead_lettered`, `unwatched` or `failed`, `watchEndsAt`, `deadLetterReason`, `failureDetails`, `watchProblem`) shows the outcome. The Checkout stays active meanwhile, its Decisions frozen and its time limit and heartbeat running; `POST /api/checkouts/:id/apply/continue` carries out the rest at the Apply's rate (also before the window ends; `409 apply_not_waiting` otherwise), and the stop endpoint returns the rest to the queue as Keep, as does the Checkout ending or being lost while it waits. A headers dead-letter exchange, no dead-letter exchange or a refused permission makes the Canary `unwatched`, which `applyConfirmation.canary` (`watchWindowMs` and the candidates with their watchability) says beforehand. A Broker Profile gains `canary: { watchWindow }`, a duration from `5s` to `10m` (default `30s`; startup refuses others), and the chart's values schema accepts it. The Canary's Audit Entry records `canary: true` and `canaryOutcome` (audit schema v9). The web app gains a Canary toggle and Message pick in the Apply confirmation, a Canary panel with a countdown, the outcome and Continue and Stop, and a Canary marker in the Audit view. (#58)
- Canary with Approval, and required Canaries. The request for Approval (`POST /api/checkouts/:id/approval-request`) accepts `canary` as an Apply does, frozen with the Decisions and the rate; `approvalRequest.canary` and the approval list's `canary` show it as `{ handle, messageId }`. Approving runs the Canary, and then the requester (`POST /api/checkouts/:id/apply/continue` or `…/stop`) or the approver (`POST /api/approvals/:checkoutId/apply/continue` or `…/stop`) continues or stops it, with no second Approval; every Audit Entry names both. A Broker Profile's `canary` gains `requiredAbove: N`: an Apply or request for Approval with more than N Replays and no Canary answers `400 canary_required` (`{ requiredAbove }`), and `applyConfirmation.canary` gains `requiredAbove` and `required`. Startup refuses a negative or fractional N; the chart's values schema accepts it. The web app shows the Canary in the approval list and view, the Canary panel with Continue and Stop on the approval view, and a Canary toggle locked on when the profile requires one. (#59)
- Failure Details from Spring AMQP and MassTransit headers. Volverán reads the headers Spring AMQP's `RepublishMessageRecoverer` (`x-exception-*`, `x-original-exchange`, `x-original-routingKey`) and MassTransit (`MT-Reason`, `MT-Fault-*`, `MT-Host-*`) write when they give up on a Message. Message summaries, the Message view and NDJSON export lines gain `failureDetails` (`null` when none; the export stays `v: 1`). Without `x-death`, the dead-letter reason falls back to the exception type and message, and the original queue to MassTransit's input queue. The new filter clause `{ "kind": "failure", "value": ... }` matches the exception type or message in any case. Queues whose name ends in `_error` are listed as dead-letter queues. The web app shows a Failure Details section (stack trace collapsed), a skipped marker for `MT-Reason: skip` and the Failure filter. See [Spring AMQP and MassTransit](docs/spring-amqp-and-masstransit.md). (#60)
- Compare two Messages. `GET /api/checkouts/:id/compare?a=<handle>&b=<handle>` (the owner) and `GET /api/approvals/:checkoutId/compare?…` (an approver of the waiting Checkout) answer `{ left, right, diff }`: both Message views and their diff, with properties and headers by name (`equal`, `changed`, `onlyLeft`, `onlyRight`), `x-death` entries by position, Failure Details by field, and the body by kind (JSON as JSON-path changes, text as line hunks, binary as the sizes and first differing byte, bodies of different kinds as `mixed`). The role and owner rules are those of the Message view; an unknown handle answers `404 message_not_found`, the same handle twice `400 invalid_request`. The web app opens a two-column comparison from a Checkout with exactly two Messages selected (Compare, or the `c` key) and from the Approval view, with differences highlighted, "Hide equal" (on for bodies over 50 lines) and, in a Checkout, Decision buttons for each side. (#62)

## [0.3.0] - 2026-10-28

Team safety (see the [roadmap](ROADMAP.md)): Roles per Broker Profile, Approval on Protected Profiles, Broker Profiles that connect with the Operator's own token, Died Again detection, NDJSON export, more dead-letter set-up checks and keyboard navigation.

**Upgrading from 0.2:**

- **Protected Profiles in Team Mode now require Approval by default.** An Apply that changes where a Message ends up on a Protected Profile waits for a second Operator. Set `requireApproval: false` on the profile to keep the 0.2 behaviour (typed confirmation only), for example for a team of one. Solo Mode is unchanged.
- **API: `setupWarning` is now `setupWarnings`.** A queue list row carries a list of set-up warnings (`[]` for none) instead of one warning or `null`, and each warning has a `severity`.
- **Roles change nothing until you add them.** A Broker Profile without `roles` keeps every signed-in Operator `admin`, as in 0.2, and startup logs a warning for it. Solo Mode ignores `roles`.
- The audit store is migrated to schema version 6 at startup. The migrations only add columns (`role`, the approver, the export's filter and Message count), which are `null` on older Audit Entries.

### Added

- Roles per Broker Profile (Team Mode). A profile's optional `roles` maps OIDC groups to `viewer` (sees the profile, its queues and Audit Entries without Discarded bodies), `operator` (also reads Discarded bodies and starts Checkouts, Decisions and Apply) or `admin` (also Restores); the highest matching role wins. The groups come from the ID token claim named by `VOLVERAN_OIDC_GROUPS_CLAIM` (default `groups`; chart value `oidc.groupsClaim`) and are fixed until the next sign-in. Routes answer `403 no_role_on_profile` or `403 role_required` (with `required` and `held`) before touching the broker, `GET /api/profiles` and Audit Entry search leave out profiles without a role, `GET /api/session` gains `roles` and (Team Mode) `groups`, and every new Audit Entry records the Operator's `role` (`null` on older entries; audit schema v4). The web app shows the actions a role does not allow as unavailable. Startup refuses unknown roles, empty group lists and non-string groups. **Upgrading changes nothing until you add `roles`:** a profile without them keeps every Operator `admin`, with a startup warning per profile ([ADR 0007](docs/adr/0007-profiles-without-roles-keep-everyone-admin.md)), and Solo Mode ignores them. Audit Entries of a profile no longer configured give the Operator the highest role they hold on any configured profile, so an Operator with no role anywhere neither finds them nor reads their bodies, and `GET /api/audit-store` answers `403 no_role` to such an Operator. (#38)
- The groups claim in the shapes identity providers send: `VOLVERAN_OIDC_GROUPS_CLAIM` takes a dotted path (`realm_access.roles` on Keycloak), a single string counts as one group, and when the ID token lacks the claim the groups are read from the provider's userinfo endpoint. A claim of any other shape, or a userinfo request that fails, gives no groups and a log warning, never a failed sign-in; startup refuses a path with an empty step. An Operator who signs in with no role on any Broker Profile sees a page saying so, listing the groups Volverán received. The Team Mode guide gains groups claim set-ups for Keycloak, JumpCloud, Okta and Entra ID (object ids, and the groups overage). (#39)
- Approval on Protected Profiles (Team Mode). An Apply with any Decision other than Keep on a Protected Profile waits for a second Operator with the role `operator` or `admin` on it. `POST /api/checkouts/:id/apply` answers `409 approval_required`; the requester confirms as before (typed queue name) with `POST /api/checkouts/:id/approval-request`, which freezes the Decisions (status `awaiting_approval`, `409 awaiting_approval` on a change) while the time limit and heartbeat keep running, and can withdraw it with `DELETE`. Approvers list the waiting Checkouts with `GET /api/approvals`, read one with `GET /api/approvals/:checkoutId` (and `/messages/:handle`), and approve it with `POST /api/approvals/:checkoutId/approve` `{ confirmQueueName }`, which runs the Apply on the requester's Checkout. Self-approval answers `403 cannot_approve_own_apply`. The Checkout view's `applyConfirmation` gains `approvalRequired`, `lastApply` gains `approvedBy`, and Audit Entries gain `approverId` and `approverName` (audit schema v5). The web app's Apply confirmation becomes Request Approval, with a waiting state and Withdraw, and a new Approvals view lists the waiting Checkouts, opens one read-only and approves it; it stays reachable (from the nav or a requester's link) while the approver has a Checkout of their own, which stays open meanwhile. A profile gains `requireApproval` (only with `protected: true`; startup refuses it otherwise). (#45)
- Reject a request for Approval with a reason: `POST /api/approvals/:checkoutId/reject` `{ reason }` (`400` without one) returns the Checkout to staging, and the Checkout view's `rejection` (`reason`, `rejectedBy`, `at`) shows it to the requester until the next request. `409 not_awaiting_approval` now says why the request no longer waits (withdrawn, approved, rejected, or cancelled by the Checkout ending, becoming lost or reaching its time limit), and approve, withdraw, reject and the Checkout's end are settled first-come. `GET /api/approvals` items gain `waitingMs`. The web app shows the rejection, the time left while waiting and a copyable link to the waiting Checkout (`/#/approvals/<checkout id>`), and the Approvals list shows waiting time, time left and the count of each Decision. (#46)
- Broker Profiles that connect with the Operator's own token (Team Mode). A profile with `credentials: operatorToken` has no `username` or `passwordEnv`: Volverán keeps the access token from sign-in in the server-side session, uses it as the password of every AMQP connection it opens for that Operator (Checkout, Restore) and as a bearer token for the management API, so RabbitMQ applies the person's own permissions and its logs show them. An approved Apply runs with the requester's token. The Audit Entry's broker user is the token claim named by `tokenUsernameClaim` (default `sub`). A broker permission refusal answers `403 broker_permission_denied` naming the resource and permission (a Restore the token may not publish included; in an Apply, a refused Replay or Move fails that Message with a reason naming the exchange and the write permission); an expired token answers `401 broker_token_expired` with `signInUrl`, and a live Checkout whose token expires becomes a Lost Checkout. Startup refuses `operatorToken` in Solo Mode and with `username` or `passwordEnv`; the chart's values schema accepts both keys. `GET /api/profiles` gains `credentials`, and `username` and `passwordEnv` are `null` on such a profile. See the Team Mode guide and [ADR 0008](docs/adr/0008-operator-token-pass-through-per-profile.md). (#49)
- Token refresh for `operatorToken` profiles. The session keeps the refresh token server-side and refreshes the access token 60 seconds before it expires (halfway through a token shorter than two minutes); every live AMQP connection the Operator opened on such a profile (a Checkout, a Restore in progress) receives the new token with `update-secret`, so a Checkout outlives the token on the same connection. When the provider refuses the refresh, the token runs out: routes answer `401 broker_token_expired`, the web app asks the Operator to sign in again, and a live Checkout ends as a Lost Checkout. Providers that issue a refresh token only for offline access need `offline_access` in `VOLVERAN_OIDC_SCOPES`. See [Token refresh](docs/team-mode.md#token-refresh). (#50)
- Died Again detection. A held Message carrying `x-volveran-replay-id` (one that Volverán Replayed, Moved or Restored and that was dead-lettered again) is flagged in the Checkout's Message list and the Message view with `diedAgain`: its replay id, how many times it has died again (followed back through the replay ids the earlier Audit Entries recorded), and the Audit Entry, action, time, Operator and source queue of the last trip out (`last`, `null` when no Audit Entry here has the replay id, e.g. another Volverán instance sent it, or when that entry is on a Broker Profile the Operator has no role on). The Checkout gains `diedAgainCount`, and the new filter clause `{ "kind": "died-again" }` selects these Messages for Select all matching. The web app shows a Died Again badge, links the Message view to the Audit Entry, offers the filter, and warns when Replay is given to a Died Again Message. No audit schema change. (#40)
- NDJSON export: the owner of an active Checkout downloads its held Messages, all of them or those matching the current filter, as one lossless JSON line each (`POST /api/checkouts/:id/export`, the Export buttons). Lines carry the properties and headers in the lossless AMQP JSON of Audit Entries, the body as base64, the decoded `x-death`, the Delivery Budget, the current Decision and the Died Again replay id. The download is streamed and changes nothing on the broker. Each export writes an Audit Entry with the new action `export`, the filter and the Message count (audit schema v6). The line format is in the README. (#44)
- Set-up check `dead_letter_exchange_missing`: the queue list warns about a queue whose dead-letter exchange (by argument or policy) does not exist in the vhost, since the broker drops every Message the queue dead-letters. The queue list header counts the vhost's set-up warnings by severity. (#41)
- Set-up check `dead_letter_unroutable`: the queue list warns about a queue whose dead-letter exchange exists but has no binding that routes its dead-letter routing key (or, without one, any routing key the queue is bound with) to a queue, and no alternate exchange, since the broker drops what the queue dead-letters. Direct, fanout and topic exchanges are evaluated, following exchange-to-exchange bindings; headers exchanges, exchanges of a plugin's type and the default exchange are never warned about. The warning carries `deadLetterExchange` and `routingKey` (`null` when the queue sets none). (#42)
- Set-up check `dead_letter_queue_drops_messages` (`loses_messages`): the queue list warns about a dead-letter queue with a message TTL or a length limit with `drop-head` overflow (the default) and no dead-letter exchange of its own, or with a queue expiry (`x-expires`), which deletes the queue and its Messages even when it has one. The warning's `settings` names which settings drop Messages. (#43)
- Set-up check `quorum_at_most_once_dead_lettering` (`may_lose_messages`): the queue list notes a quorum queue that dead-letters with the default `at-most-once` strategy (or `at-least-once` without the `reject-publish` overflow it needs), which can lose a dead-lettered Message, and explains the fix. Both checks read queue arguments and policies. (#43)
- Keyboard navigation. Queue list: `j`/`k` or the arrow keys move, Enter starts a Checkout on the focused queue. Checkout: `j`/`k` or the arrow keys move and the Message view follows, Space adds the focused Message to the Selection or takes it out, Shift+↑/↓ extends the Selection, Shift+`D`/`R`/`M`/`K` assign Discard, Replay, Move or Keep to the Selection or else the focused Message, `/` focuses the filter, Escape closes a prompt or clears the Selection, and `?` lists every shortcut. The Apply, Request Approval, Approve and Reject confirmations take the focus when they open (the typed queue name or reason, or else Cancel), close with Escape and give the focus back to the button that opened them. No key Applies, approves, rejects or Restores, and shortcuts do nothing while a text field has focus. The Message list is a listbox for screen readers, with the focused Message as its active descendant, and keyboard focus is always visible. (#47)

### Changed

- **Protected Profiles in Team Mode now require Approval by default.** After upgrading, an Apply that changes where a Message ends up on a Protected Profile waits for a second Operator, and startup logs which profiles require it. A team of one, or a profile where typed confirmation is enough, sets `requireApproval: false` on it to keep the v0.2 behaviour. Solo Mode is unchanged. (#45)
- Discard and Move open a prompt for the reason or the destination, the same prompt their keys open, instead of taking them from fields in the Decision bar. (#47)
- **API: a queue list row's `setupWarning` (one warning or `null`) is now `setupWarnings`**, a list (`[]` for none), so a queue shows every warning that applies. Each warning gains a `severity`: `loses_messages` or `may_lose_messages`. The delivery-limit warning keeps its code, `messages_dropped_at_delivery_limit`, and now also fires when the queue's dead-letter exchange does not exist. The queue list response gains `setupWarningCounts`, the warnings of the whole vhost by severity, whatever the search or dead-letter queue filter. (#41)

### Fixed

- Development: run from source (`npm run dev`), the server no longer serves the unbuilt `src/web` on `:8080`, which showed a blank page (`main.tsx` blocked for its MIME type). It serves no web app and answers `404` with a pointer to the Vite dev server on `http://localhost:5173`. `npm start` and the image still serve the built `dist/web`. (#32)

## [0.2.0] - 2026-10-27

Deployable on Kubernetes (see the [roadmap](ROADMAP.md)). The image and its behaviour are unchanged for `docker run` and Compose apart from the health endpoints and the numeric user.

### Added

- Helm chart `charts/volveran`, published to `oci://ghcr.io/volveran/charts/volveran` with the chart version equal to the Volverán version. It always runs Team Mode, listening on all interfaces inside the pod: one replica with the `Recreate` strategy (any other `replicaCount` is refused, citing ADR 0003), no service account token, a pod that passes the `restricted` Pod Security Standard (numeric non-root user, read-only root filesystem with an `emptyDir` at `/tmp`, no capabilities, `RuntimeDefault` seccomp), and liveness, readiness and startup probes on `/healthz` and `/readyz`. The OIDC client secret, the session secret and broker passwords come only from existing Secrets (`existingSecret`, `brokerProfiles.passwordsSecret`), never from values. Broker Profiles are written inline (a chart-managed ConfigMap whose changes roll the pod) or read from an existing ConfigMap. The audit store gets a PersistentVolumeClaim kept on uninstall, or an existing claim; `persistence.enabled: false` uses an `emptyDir` and warns in the install notes. Also: private CA bundles for brokers and the OIDC provider (`caBundles`), Volverán's settings as named values and an `extraEnv` escape hatch, image digest pinning and pull secrets, scheduling options, a values schema, install notes with the redirect URL to register, and every value documented in the chart README. Missing OIDC values or Broker Profiles fail at render time with a message naming the value. (#18, #22)
- Exposure: an optional Gateway API `HTTPRoute` (parent references, host names) and an optional `Ingress` (class, hosts, TLS Secrets, annotations); neither renders by default. (#20)
- An optional NetworkPolicy admitting only the peers you name to the pod, with optional egress rules that always allow DNS. (#21)
- Health endpoints: `GET /healthz` answers `200` whenever the process serves HTTP; `GET /readyz` answers `200` once configuration is loaded, OIDC discovery has succeeded (Team Mode) and the audit store is open (the server only starts listening after that), and `503` once shutdown starts. Both answer without a session in either mode, never check a broker, return only `{"status":"ok"}` and are left out of the request log. (#17)
- Signed artifacts: a version tag publishes the Helm chart next to the image, and the release workflow signs both with keyless cosign using its GitHub OIDC identity (verification commands and the Flux `matchOIDCIdentity` in the workflow's header). The release fails before anything is pushed unless the tag, `package.json` and the chart's `version` and `appVersion` agree. A pre-release tag (`v0.2.0-rc.1`) publishes a pre-release chart version. (#23)
- Kubernetes guide (`docs/kubernetes.md`): installing with Helm or Flux CD, values, exposure, secrets, private CAs, upgrades (a deploy signs everyone out and ends open Checkouts) and backup and restore of the audit store. A Flux CD example (`examples/flux/`): a namespace enforcing `restricted` pod security, a cosign-verified `OCIRepository` following `0.2.x`, a `HelmRelease` with OIDC, inline Broker Profiles, persistence and an `HTTPRoute`, and SOPS-encrypted Secrets with the reader's own age key. The Team Mode guide gains a Kubernetes section, and the README quick start the Helm install. (#24)
- A kind-cluster smoke test in CI (`npm run test:smoke`): the chart installs under restricted pod security, an Operator signs in and Applies a Checkout, the audit store survives a pod restart, and a changed Broker Profile rolls the pod. (#19)

### Changed

- The image runs as the numeric user `1000:1000` (the same `node` user as before), so Kubernetes can verify `runAsNonRoot`. Existing `/data` volumes stay writable. (#17)

## [0.1.0] - 2026-10-24

First release: triage core and identity (see the [roadmap](ROADMAP.md)).

### Added

- Solo Mode: no sign-in, listens on a loopback address only and refuses to start on any other. The Operator is taken from `VOLVERAN_OPERATOR`, else `USER`. (#2)
- Broker Profiles from a YAML file, with passwords from environment variables, `amqp`/`amqps` and `http`/`https`, and an optional CA file. (#2)
- Queue list per Broker Profile and vhost, with approximate depth, consumers and type; dead-letter queues first, streams marked as not available. (#2)
- Distinct connection errors for bad credentials, an unreachable broker, missing permissions and TLS failures. (#2)
- Docker image: multi-stage, runs as a non-root user and works with `--read-only`; Solo Mode runs with `--network host`. (#2)
- Release workflow: a tag `v<version>` publishes a multi-arch image (`linux/amd64`, `linux/arm64`) to `ghcr.io/volveran/volveran` as `<version>` and `latest`, with an SBOM and provenance attestations. (#13)
- README quick start and `docker-compose.example.yml`. (#13)
- Checkout: holds the N oldest ready Messages of a classic or quorum queue (N from a passive declare), unacknowledged, capped at 1,000 Messages or 100 MB of bodies (`VOLVERAN_CHECKOUT_MAX_MESSAGES`, `VOLVERAN_CHECKOUT_MAX_MB`); the UI shows "1,000 of ~N held". One Checkout per queue across instances, through an exclusive lock queue `volveran.checkout.<queue>` (needs configure permission on `^volveran\.`); a second one is refused and names the holder. One active Checkout per Operator. Ending it returns every Message to the queue in order, without using up Delivery Budget. Message list with `message_id`, routing key, timestamp, dead-letter reason, original queue and Delivery Budget on quorum queues; Message detail with properties, headers, `x-death` history and the body as JSON, text or hex and base64. (#3)
- Checkout time limit (`VOLVERAN_CHECKOUT_TIME_LIMIT_MINUTES`, default 30) shown as a countdown, and a browser heartbeat (`VOLVERAN_CHECKOUT_HEARTBEAT_SECONDS`, default 120): either ends the Checkout cleanly. On quorum queues the consumer carries `x-consumer-timeout` one minute past the time limit as a backstop. A Lost Checkout (connection dropped, channel closed, consumer cancelled by the broker) is reported with the Messages back in the queue, and Apply is refused. A queue with live consumers (counted with a passive declare) needs an explicit override to be checked out. (#4)
- Selection, filters and Decisions: filter the held Messages by routing key, header, `x-death` reason, original queue, body text and JSON path (a value at a path in a JSON body), select all matching, and give the Selection a Decision (Discard with a reason, Replay, Move or Keep). Decisions are held on the server for the Checkout, survive a browser reload, and are summarised for the Apply confirmation. Replay is unavailable, with the reason, for a Message with no `x-death` history. (#5)
- Protected Profiles (`protected: true` in a Broker Profile): highlighted throughout the UI; an Apply with any Decision other than Keep, and every Restore, needs the queue name typed, checked by the API as well as the UI. (#9)
- Team Mode (`VOLVERAN_AUTH=oidc`): sign-in through any OIDC provider (authorization code flow with PKCE, server-side sessions in an HTTP-only cookie, sign-out), every API route needs a session, and the Operator is the signed-in person (`sub` stored, email or name shown). Configured with `VOLVERAN_OIDC_*` and `VOLVERAN_SESSION_SECRET`; guide in `docs/team-mode.md`. (#11)
- Dead-letter set-up check: the queue list flags a quorum dead-letter queue with a delivery limit and no dead-letter exchange, where Messages past the limit are dropped, and suggests `delivery-limit = -1` or a dead-letter exchange. (#12)
- Apply with Discard: each Discarded Message is written in full (body, properties, headers) to the audit store with a durable commit, then acked; every other Message goes back to the queue in order. Each Message gets its own outcome (done, failed and kept, not attempted); there is no rollback, and Apply is refused on a Lost Checkout. (#6)
- Audit store: SQLite with schema migrations in `VOLVERAN_DATA_DIR` (`/data` volume in the image); an Audit Entry per action records the Operator, broker user, Broker Profile, vhost, queue, `message_id`, action, reason, outcome and time. Read through `GET /api/audit-entries` and `GET /api/audit-entries/:id`. (#6)
- Replay: a Message is published through the default exchange to the queue that dead-lettered it (its latest `x-death` entry), never to other queues bound to its routing key, on a separate confirm channel with `mandatory`, and acked only once confirmed without a return. `CC`, `BCC`, `x-death`, `x-first-death-*`, `x-last-death-*`, `x-delivery-count` and `x-acquired-count` are removed and `x-volveran-replay-id` and `x-volveran-from` added; the Audit Entry keeps the original headers. A Replay the broker cannot route fails and the Message falls back to Keep. (#7)
- Move: send Messages to another existing queue of the same vhost, or to an existing exchange with a routing key (delivered by its bindings), picked from the queues and exchanges of the vhost (`GET /api/profiles/:profile/vhosts/:vhost/move-destinations`). Same publish and header rules as Replay; the Audit Entry records the destination and the original headers. A destination that does not exist is refused when the Decision is given; an unroutable Move, or a destination deleted since, fails and the Message falls back to Keep. (#8)
- The Audit Entry of a Replay or Move records its replay id (`x-volveran-replay-id`), so a Message that dies again can be traced back: `GET /api/audit-entries?replayId=`. Audit store schema version 2. (#8)
- Audit browsing: search Audit Entries by Broker Profile, queue, `message_id`, action, Operator and date (`GET /api/audit-entries?profile=&queue=&messageId=&action=&operator=&from=&to=`), and by replay id (`replayId=`, #8), in a new Audit view of the web app that also shows each replay id. (#10)
- Restore: a Discarded Message is republished from its Audit Entry, byte for byte, to the queue it was Discarded from (default exchange) or to another existing queue, with the same header rules as Replay (`x-volveran-replay-id`, `x-volveran-from`), on a confirm channel with `mandatory`. Each Restore writes its own Audit Entry (action `restore`, linked to the Discard, with the replay id it published with) as the signed-in Operator; it is refused while the Discard is still being Applied, once it has been Restored, and, unless the Operator accepts a possible duplicate, when the Discard's outcome is pending or uncertain. A Protected Profile needs the destination queue name typed. `POST /api/audit-entries/:id/restore`. (#10)
- Retention of Discarded bodies: kept for 30 days or until they reach 1 GiB in total, whichever comes first, oldest evicted first, checked at startup and hourly (`VOLVERAN_BODY_RETENTION_DAYS`, `VOLVERAN_BODY_RETENTION_MAX_BYTES`, `VOLVERAN_BODY_RETENTION_INTERVAL_MINUTES`). Audit Entries are kept indefinitely; an evicted one shows "body expired" and Restore is refused with the reason (`410 body_expired`). `GET /api/audit-store` reports the stored size against the limit, and the Audit view warns at 90 %. Audit store schema version 3 adds `restore_of` and `body_expired_at`. (#10)
- Broker-facts suite: every fact in `docs/rabbitmq-behaviour.md` that the design depends on is checked against a real RabbitMQ, on every push against the pinned image and weekly against the latest `rabbitmq:4-management`. (#1)
